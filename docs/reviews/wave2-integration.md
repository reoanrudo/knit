## 1. エグゼクティブサマリ

第三者6視点(アーキテクチャ/品質/エッジケース/性能/セキュリティ/UX)のレビュー結果、**「動いているから正しい」の相当部分が単一運用経路(絶対位置モード+edge切替+常時接続+ディスプレイ構成不変)に支えられている**ことが確認された。最重要の結論は次の3点。

1. **本番が既定開発トークン `seamless-desk-dev` で稼働していることが実機確認で確定**(稼働中 sd-mac に SEAMLESS_DESK_TOKEN 未設定・.env ファイルなし・.env を読むコードもリポジトリに存在しない)。さらに Mac のリッスンが `0.0.0.0` のため、「防御は Tailscale のルーティング偶然に依存している」状態が現在進行形である(レビューEの指摘が現実化)。
2. **相対モード(rel)は一度も動作検証されていない**。ウォッチドッグが rel モードで必ず誤発火し、切替後数秒で強制復帰する(4レビューが独立に同一結論)。「守るべき動作」の一方が実際には壊れている。
3. **「戻れない」バグ5回の根本原因は構造にある**: WIN_MODE の状態遷移が6箇所に分散し、後処理(カーソル復帰)を各呼び出し側の規律と6本の保険スレッドに依存させている。切断という正規経路ですら leave を呼ばず自己修復スレッドの「たまたま」に頼っている。

UX評価は **5.0/10**。正常系の設計(絶対位置モード・IME方向指定・JISキーマップ)は第三者目線でも Deskflow/Logitech Flow に対する固有価値と認められた一方、異常時の完全な不可視性(全てログ専用)が「まだストレスを覚える」「本質がわからない」の正体と診断された。

なお、資料(docs/)と実コードの数値食違いは**全6レビューが独立に指摘**(ガード400ms/同期16イベント/窓700ms/ping 3s-10s/バックオフmax3s/IME実装方式/現行IP)。docs 全面書き直しはリファクタの前提条件とする。

## 3. 収束マトリクス(複数レビューが独立に到達した指摘=高確度)

単一レビューだが致命判定のもの:
- **C-S2(致命)**: タップコールバックがランデブーチャネル tx.send でブロック→半開時に Mac 全入力フリーズ(復帰経路も全滅)
- **C-S3(高)**: WIN 中のアクセシビリティ権限剥奪で6復帰経路が同時死(唯一の脱出不能状態)
- **F-第2位(強い推測)**: cmd+Tab の Alt 押しっぱなし残留(確定ブロック到達不能)。「まだストレス」の未説明成分の最有力候補。実機検証を最優先で行うこと
- **B-P1-1(確定)**: autorelease pool 無しによる ObjC オブジェクト確定リーク(画像同期で数MB/回)
- **D-F1**: Win クリップ監視が200ms毎に全量コピー+b64エンコード、5MB超過画像で無限再試行(推定130-150MB/sの定常メモリトラフィック)

## 5. GUI 方式の裁定(Wave3 で実装)

レビューA(§2.3)とレビューB(unsafe 棚卸し)の見解が一致したため、プロンプトGの3案から **(b) objc2 + objc2-app-kit** を選定:

- **同一バイナリ・同一メイン RunLoop**: 現行 tap は kCFRunLoopCommonModes に載っており、CFRunLoopRun を NSApp.run に置換するだけで NSStatusItem と共存可能(A)。GUI クラッシュ懸念より別プロセス IPC の運用複雑化を排除。restart-mac.sh の起動検知がそのまま使える
- **新規 GUI コードのみ objc2-app-kit、既存 NSPasteboard transmute 方式は温存**(混在可能)。全書き換えはしない
- **静的リンクの確認が初期タスク**(クロスビルドへの影響は Mac ネイティブのみなので影響小)
- GUI が触る境界は switching::snapshot() / net::status() / diag の3点に限定(モジュール分割 Phase 5 との依存関係: **分割が先、GUI が後**。逆順で作ると中核を直接触る UI コードが再生産される)
- GUI 機能の優先順は F §5 に従う: ①状態常時可視(接続/モード/RTT/BUILD_ID) ②セットアップウィザード(権限案内・トークン配布・LaunchAgent) ③設定UI(SEAMLESS_*のフロント、環境変数フォールバック) ④失敗履歴ビューア ⑤レイアウト可視化

## 6. Wave3 実行計画(案)

原則: 各ステップで `cargo build(両ターゲット) → cargo test → restart-mac.sh → deploy-win.sh → verify.sh 7項目` を回す。1機能ずつコミット(メッセージは「改善ループN(第8セッション)」形式を継続)。

- **Step 0: 承認とトークン運用の決定**(§7 のユーザー決定事項)
- **Step 1: P0-1 セキュリティ最小セット**(両側同時デプロイ。トークン生成・setx 配布手順書含む。verify.sh に「トークン未設定警告なし」チェック追加)
- **Step 2: P0-2〜P0-4 の機能バグ修正**(各々再現確認→修正→検証の順。rel の `[watchdog]` 再現、WIN 中 taskkill での復帰ログ、画像コピー中の pong 健全性)
- **Step 3: P1 のうち軽量なものから**(P1-1, P1-3, P1-10, P1-12 は合計で半日規模。P1-2/P1-6/P1-8 は1日規模)
- **Step 4: テスト足場+verify.sh 拡張**(P2 のテスト項目。モジュール分割の前提)
- **Step 5: docs 全面書き直し**(X8。「守るべき動作」の定義を実装に一致させる)
- **Step 6: モジュール分割(A 案 Phase 1〜7。ストラングラー方式、移動コミットとロジック変更コミットを分離)
- **Step 7: GUI(objc2-app-kit。メニューバー状態表示→設定→ウィザードの順)**

Step 6/7 は Step 1〜5 の完了が前提。Step 1〜3 だけでも現行運用のリスクと「たまたま動いている」層の大半を排除できる。

## 7. ユーザー決定事項(Wave3 起動前に回答が必要)

1. **トークン運用**(P0-1): (推奨)128bitランダムトークン生成→必須化→setx 配布。既定値運用の継続はセキュリティレビュー上認められない
2. **rel モードの維持・廃止**: 維持するなら P0-2 の修正が必須。廃止するなら「守るべき動作」の定義変更と docs 更新
3. **P1-13(プロトコルVERSION 3・HMAC チャレンジ)の実施要否**: Tailscale ACL での代替も可
4. **EDGE_TAPS=3 の扱い**: 実装するかバリデーションを 1..=2 に狭めるか(A-L3)
5. **Mac→Win 画像クリップボードを GUI 化スコープに含めるか**
6. **Wave3 の開始範囲**: Step 1〜3(リスク是正)のみ先に実施し、Step 4〜7(再構築)は別途承認、または一括実施
