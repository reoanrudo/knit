# Knit ドラッグ&ドロップ — 非ファイルの運搬(画像・URL・テキスト)の設計

作成: 2026-10-19 / 対象: Mac⇄Windows のドラッグでファイル以外を運ぶ
状態: 設計 + 共通層の実装(N3a)。OS のペーストボード側(N3b〜N3e)は実機で確かめながら刻む。

## 0. 結論(3行)

1. 運搬物を `PayloadKind { File, Image, Text, Url }` に一般化し、**テキスト/URL は予告・目録にインライン(64KiB まで)**、画像は既存の大容量経路で運ぶ。種類は `serde(default)` で旧版は未知フィールドとして無視する。
2. **非ファイルは版18の相手にだけ送る**(版ゲート)。旧版はこれまでどおりファイルのみで、混在しても壊れない。
3. 受け渡しの最終段(OS のペーストボード/ OLE データオブジェクト)は各 OS の責務にする。共通層は「何を・いくつ・いつ断るか」だけを持ち、Windows は `CF_HDROP` / `CF_UNICODETEXT` / `CF_DIB` を種類で登録、Mac は `NSPasteboardTypeFileURL` / `NSPasteboardTypeString` / `public.png` を作り分ける。

## 1. 現状

- 掴みドラッグの予告(`DragOffer`)と目録(`ManifestEntry`)は**名前とサイズだけ**で、ファイル/フォルダのみ(設計書 §I7/I8)。
- 受け側は Windows が `CF_HDROP`、Mac が `NSURL` のみを受ける。ファイル以外を掴んでも「ファイルの転送だけ」になり、`SKIPPED_NOTICE`(「通常のファイルとフォルダだけ」)で断る。
- 画像の**実体**を運ぶ部品はクリップボード経路(`IMAGE_BEGIN/END`)に既にある。テキストを運ぶ部品は無い。
- 未対応の記録: ランナップ G5(画像/URL/テキストを掴むと未対応)。ユーザーの声は「ファイル以外も掴みたい」が主で、V1 の「片方向」や V7 の「型も重さも関係なく動かない」に通じる。

## 2. 設計

### 2.1 共通層(実装済み)

- `drag::PayloadKind`(File/Image/Text/Url)と `drag::Payload { kind, name, size, mtime, inline }`。
- `PayloadKind::from_mime` で OS の形式判定を1箇所へ寄せる。`is_inline()` は Text/Url。
- 上限: インラインは `MAX_INLINE_PAYLOAD = 64KiB`。**黙って切り詰めない**(超えたら断る)。画像は `bulk::MAX_IMAGE`(64MiB)。
- `Payload::validate()`: 空の Text/Url・サイズ不一致・ファイルへの inline・上限超えを弾く。

### 2.2 運搬路

| 種類 | 予告・目録 | 実体 | 受け側の公開先 |
|---|---|---|---|
| File | 名前・サイズ・mtime(従来) | 大容量経路(bulk) | 受信フォルダ/ドロップ先 |
| Image | 名前・サイズ・mtime | 大容量経路の画像(bulk の Image) | クリップボード(画像)+ドロップ先が対応すれば画像 |
| Text | inline 本文(64KiB まで) | 本文そのもの(追加転送なし) | クリップボードのテキスト、またはドロップ先へ直接 |
| Url | inline 本文 | 本文そのもの | クリップボードの URL、またはリンクとしてドロップ先へ |

- 予告・目録に `kind` を載せる(`serde(default)` で旧版は File 扱い)。
- 非ファイルは `peer_features(ver).resume` と同じ版18の相手にだけ送る。旧版へは送らない。

### 2.3 OS 側の責務(N3b 以降)

- **Windows(受け)**: ドロップの data object に種類で `CF_HDROP` / `CF_UNICODETEXT` / `CF_DIB` を登録する。遅延提供(W1)と同じく「先に受理して、実体は後から」。対応アプリが無い/非対応ならクリップボードへ入れて「⌘V / Ctrl+V で貼り付け」と知らせる(黙って失敗にしない)。
- **Mac(送り)**: `NSDraggingSession` の item を種類で作り分ける(`NSURL` / `NSString` / `NSImage`)。
- **Mac(受け)** / **Windows(送り)** は対称に同じ型を使う。

## 3. 互換と版ゲート

- `kind`/`inline` は JSON の未知フィールドなので旧版は無視する。**ただし非ファイルのデータを旧版へ流すと「名前だけのファイル」として壊れる**ため、送信側が版で止める(`PayloadKind::is_inline()` の項目は版18のみ)。
- ミニマム版は据え置き(11)。旧版同士の通信は影響を受けない。

## 4. 受け入れ基準(N3)

| # | 基準 | 証明 |
|---|---|---|
| N3-AC1 | テキストを掴んで渡すと、受け側でテキストとして貼り付けられる(内容が一致) | 実機の往復。クリップボード/メモ帳 |
| N3-AC2 | URL はリンクとして扱える(文字列としても一致) | 実機(ブラウザのアドレス欄) |
| N3-AC3 | 64KiB を超えるテキスト・空・サイズ不一致は**理由つきで断る**(無言にしない) | ループバックの表テスト |
| N3-AC4 | 旧版の相手には非ファイルを送らない(ファイルは従来どおり) | 版ゲートの表テスト+実機(旧ビルド) |
| N3-AC5 | 画像はクリップボード経路と同じ実体で渡り、ハッシュが一致する | ループバック+実機 |

## 6. やらないこと

1. リッチテキスト(書式)・複数画像の一括・任意 MIME(BMP 以外の画像形式変換)は対象外。
2. 非対応アプリへの「ドロップで直接挿入」は OS の制約に従う。できなければクリップボード経由(理由を通知)。
3. インラインの切り詰め(上限超えは断る)。

## 7. 弱点・未検証(正直に)

- **OS のペーストボード側はこのマシンでは確認できない**(Windows はビルド不可、Mac のドラッグは目視が要る)。N3b〜N3e は実機のランナップが前提。
- Windows の遅延提供(W1)と種類の組み合わせは未検証。特に「受理だけ先にして、テキストを後から」は OLE のデータオブジェクトの寿命に依存する。
- クリップボード経由のフォールバックは、利用者から見ると「ドロップしたのに貼り付けが必要」に見える。通知で明示するが、理想ではない(声: V1/V3 の「無言にしない」を優先)。
- 画像の上限(64MiB)はクリップボード経路の値を流用しており、ドラッグの大容量経路の上限(10GiB/ファイル)とは別。画像を10GiB級で運ぶ需要は未検討。
