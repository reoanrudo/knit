## A. 信頼性・可用性

### A-1【P1】ワーカースレッドのパニック隔離がない
- **現状**: `crates/mac/src` に `thread::spawn` が **49箇所**。`catch_unwind` は `android-bridge` の1箇所のみ。
- **影響**: 入力送信・音声・クリップボード監視などのスレッドが panic すると、その機能が**アプリ再起動まで無言で死ぬ**(GUIは生きているので気づきにくい)。
- **提案**: 重要ループ(入力送信・音声・クリップ監視・接続維持)を `catch_unwind` で包み、panic を記録して**指数バックオフで再起動**する薄い supervisor を入れる。失敗は `notify()` で1回だけユーザーへ知らせる。
- **検証**: supervisor の単体テスト(`cfg(test)` フックで panic を注入し、再起動回数と記録を検証)。

### A-2【P2】再接続が固定待ちでバックオフもジッタもない
- **現状**: `session.rs` に `sleep(300ms)` / `sleep(1500ms)` / `sleep(500ms)` の固定待ちが散在(479-585行)。
- **影響**: Wi-Fi が不安定な環境で**再接続の同時多発**(複数端末)や、逆に復帰が遅い。
- **提案**: 指数バックオフ+ジッタ(例 0.3→0.6→1.2→2.4秒、上限5秒)に統一し、待機中はメニュー状態行へ「再接続中(n回目)」を出す。
- **検証**: バックオフ列を純関数に切り出して単体テスト。

### A-3【P2】エラー握り潰し 219箇所のうち「入力経路」の棚卸し
- **現状**: `let _ = ` が 219箇所。多くは意図的な best-effort だが、**送信失敗を無言で捨てている**箇所があると「入力が止まった」ことに気づけない。
- **提案**: 入力送信・音声供給・ファイル書き込みの3経路に限定して監査し、**状態が変わった時だけ**1行ログを出す(毎イベントは出さない)。
- **検証**: 監査対象を列挙したチェックリストと、失敗注入テスト(書き込み先を閉じる等)。

## B. 観測性・サポート性

### B-1【解決済み・誤りの訂正】Windows のログローテーション
- 当初「実経路(vbs)ではローテーションが死んでいる」と書いたが、**確認したところ修正済み**だった。
  `win-dist/run_knit.vbs` は `run_knit.bat` を起動し、その bat が
  `knit-win.log` → `knit-win.log.old` の世代退避と `>> knit-win.log` のリダイレクトを行っている
  (`win-dist/run_knit.bat:4-6`、vbs 冒頭に「旧版は exe を直接リダイレクトしていたため…
  レビュー Wave1 X6 の修正」と記録あり)。**この項目は対応不要**。

### B-2【P3】診断バンドルがログ末尾に依存
- **現状**: `diag.rs:57` が `/tmp/knit-mac.log` の末尾を読む。ログが空(起動直後・ローテーション直後)だと情報が薄い。
- **提案**: 直近の接続イベント・adb 実行履歴・通知履歴を**メモリ上のリングバッファ**に持ち、診断時に一緒に出す。

## C. UX・分かりやすさ

### C-1【P2】主要な失敗モードの「ユーザーに見える説明」を棚卸し
- **現状**: `notify()` は多数の経路にある(mac: clip 14 / files 21 / gui 15 / conn 3 …)。一方で失敗の種類(トークン不一致・ファイアウォール・端末ビジー・ディスク満杯・権限)ごとに**文言と次の行動**が揃っているかは未検証。
- **提案**: 上位5つの失敗モードについて「何が起きたか+次に何をすればよいか」を1文で示す表を作り、文言を統一。可能なら「診断を実行」ボタンから診断バンドルを開けるようにする。
- **検証**: 失敗を注入して通知文言を確認するテスト(既存の通知経路にフックがあるかは要確認)。

### C-2【P3】初回セットアップの分かりやすさ(未検証)
- **現状**: `gui/setup.rs` / `win/src/tray/setup.rs` が存在。実際の初回体験は**この環境では評価できない**(GUIを起動して人手で確認が必要)。
- **提案**: セットアップ完了条件を明文化し、各手順に「今どこにいるか」を出す。

## D. セキュリティ

### D-1【P2】権限まわりの「作った後」の穴を総点検
- **現状**: 履歴は作成時 0600 ✓。ただし他の生成物(設定・診断バンドル・トークン・Android 用の一時ファイル)が**同じ基準を満たしているかは未検証**。`android.rs` は `std::env::temp_dir().join(name)` に**画像を平文で一時書き出し**している(ループ12で確認)。
- **影響**: 共有 Mac で他ユーザーが画像を読める可能性(既定 umask 依存)。
- **提案**: 一時ファイルも 0600 で作る(`write_private` 相当を使う)。生成物一覧を作り、権限を機械的に確認するテストを追加。
- **検証**: 一時ディレクトリに作って `mode & 0o077 == 0` を assert。

### D-2【P3】診断バンドルに機密が混ざらないことの確認
- **現状**: ログに機密は見つからなかったが、診断バンドルが**履歴本文やトークンを含めていない**ことの明示的なテストは未確認。
- **提案**: 診断バンドル生成のテストで「トークン文字列・クリップ本文が含まれない」ことを assert。

## E. リソース・コスト

### E-1【P2】画像1枚が 33MB(4K)で、512MiB 上限にすぐ届く
- **現状**: 履歴画像は BMP で保存(`clip.rs`)。4K で 33MB/枚 → 512MiB 上限は**約15枚**で到達し、以降は毎回 prune(削除)が走る。Windows 側が DIB として読むため**形式だけを変えるのは不可**(性能ループ11で確認)。
- **提案**: (a) 上限を枚数・バイトの両方で見直す、(b) PNG 保存へ移すなら**両OS同時の版上げ**(v17)として設計、(c) 履歴に載せるのは**縮小版(長辺2560等)+原本は別管理**。
- **検証**: 上限到達時の prune 時間と、ユーザーに見える影響(履歴の画像が消える)を計測。

### E-2【P3】/tmp のログは再起動で消える
- **現状**: Mac のログは `/tmp/knit-mac.log`(macOS は再起動・一定期間で削除)。
- **提案**: 障害調査用に、直近のセッションログを `~/Library/Logs/knit/` へも残す(または診断時にコピー)。

## F. テスト・検証体制

### F-1【P1】Android 橋渡しのテストが 6件しかない
- **現状**: `crates/android-bridge` は 1ファイル 6テスト。`mac/android.rs` は 1769行で adb 経路が中心。
- **提案**: 性能ループ12で作った**スタブ adb 方式を共通ハーネス化**し、push/clipboard/scan の経路を実機なしで検証できるようにする(既に1本成功している)。
- **検証**: スタブ経由で「起動回数」「引数」「失敗時の戻り値」を assert。

### F-2【P2】Windows 側のテストが薄い(23件/15ファイル)
- **現状**: CI は Windows で走っているので**テストを足せば自動で守られる**。
- **提案**: 入力変換(`input.rs`)・トレイ状態・設定の往復を優先して追加。

### F-3【P2】回帰検知が手動(ベンチをCIで回していない)
- **現状**: 計測器は `examples/perf-*.rs` と `tests/perf_image.rs` に揃っているが、**手で実行**するだけ。
- **提案**: `scripts/bench.sh` で全計測をまとめて表形式で出力し、CI では代表3本(転送・画像・履歴)を実行して**基準値から20%超の悪化で失敗**させる(閾値はコミットした基準ファイルと比較)。

## G. 保守性・構造

### G-1【P2】巨大ファイルの分割
- **現状**: `mac/tap.rs` 3270行、`mac/main.rs` 2000行超、`android.rs` 1769行、`audio.rs` 1751行。`gui/` は既に分割が進んでいる。
- **提案**: 変更頻度の高い領域から段階分割(例: `android.rs` → adb / display / input / clipboard の4モジュール)。**振る舞いを変えない移動のみ**のコミットにする。
- **検証**: 移動のみなら `cargo test` が同一結果。

### G-2【P3】重複実装の除去(今回1件発見)
- **現状**: 性能ループ10で `dib_to_rgba` の**二重実装**を発見し統合(片方はデッドコードだった)。
- **提案**: 「同じ処理が2箇所」を継続的に潰す小さなループを回す(テストで同一性を担保)。

## H. 相互運用・更新

### H-1【P2】更新の失敗時復旧を確認
- **現状**: 署名検証(ed25519 + sha2)は実装済み。**失敗時のロールバック**(壊れた版を入れた後の戻し方)は未検証。
- **提案**: 「更新失敗→前版で起動」の経路をテスト(署名不一致・途中で切れた zip・ディスク満杯)。

### H-2【P3】版交渉のテストを厚くする
- **現状**: `MIN_VERSION` による後方互換の設計は良い。混在環境(旧 Windows + 新 Mac)の組み合わせテストは限定的。
- **提案**: 版の組み合わせ表を作り、送らない/無視するの分岐をテーブル駆動テストにする。

## 優先順位(推奨)

| 順 | 項目 | 理由 |
|---|---|---|
| 1 | **A-1 パニック隔離** | 常駐アプリで「無言で機能が死ぬ」のは最も困る |
| 2 | **F-1 スタブ adb の共通ハーネス化** | 実機なしで Android 経路を守れる(既に1本成功) |
| 3 | **D-1 一時ファイルの権限** | 実害(共有 Mac での情報漏れ)になり得る |
| 4 | **B-1 Windows のログローテーション** | 常駐でディスクを圧迫しうる |
| 5 | **F-3 ベンチの CI 回帰検知** | 今回の改善を将来守る |
| 6 | A-2 / A-3 / C-1 / E-1 / F-2 / G-1 / H-1 | 効果は大きいが設計判断を伴う |

## 進め方の提案

- 各項目を「1ループ=1テーマ」で、**計測またはテストで効果を示せたものだけ採用**する(性能ループで確立した規律をそのまま使う)。
- 実機・GUIが必要な項目(C-2、一部の H-1)は**あなたの手動確認**が前提になるため、先に「自動で検証できる項目」から着手するのが効率的。
