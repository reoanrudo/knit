# Knit ドラッグ&ドロップ体験の摩擦棚卸し(ユーザー視点)

- 作成: 2026-10-18 / 担当: user-advocate(task-2)
- 立場: 毎日 Mac と Windows を横並びで使い、ファイルを行き来させるユーザー
- 方法: 実コードを読んで `file:line` を根拠にした。**cargo build / cargo test は未実行**(コード変更しないため)。実行して確かめていない挙動は「未確認」、コードから論理的に導いただけのものは「推理」と明記した。
- 対象は現行実装(Mac→Win の掴みドラッグ、Win→Mac の掴みドラッグ、Finder の ⌘C、Windows 側の受け取り)。

---

## 0. 結論(先に3行)

1. **一番痛いのは「掴んで境界に持って行ったのに、何も起きずに Mac のドラッグに戻る」**。理由は画面に出ず、通知(数秒で消えるバナー)だけ。手はマウスを握ったままで、やり直しの判断ができない。
2. **Win→Mac は「離すまで待たされる」設計**で、待ち時間と残量が手元に一切出ない。8MB 以下は開始通知すら無い。
3. 成功したときの作りは丁寧(スキップ・同名変更・保存失敗・中断の取りこぼしを通知で潰している)。**改善はこの「無言を作らない」文化を壊さずに、掴み〜離すの間の可視化を足す方向であるべき。**

---

## 1. 摩擦の一覧(頻度 × 痛みの降順)

評価は「頻度(毎日〜たまに)」×「痛み(壊れたと思う/戻せない/待たされる)」。上ほど先に直す価値がある。

### F1. 掴みが拒否されたときの理由が画面に出ず、手が離せない【頻度: 高 / 痛み: 最大】

**何が起きるか**
「ファイル経路がまだ準備中」「確認がまだ終わっていない」「集計条件が変わった」「前の転送中」「渡せるものが無い」のどれかで掴み渡しが拒否されると、境界を越えずに Mac 側のドラッグが続く。ユーザーから見ると「端まで持って行ったのに何も起きない」だけ。

**根拠**
- 拒否時は必ず `notify(...)`(macOS の通知センターのバナー)だけで、カーソル/ウィンドウ/メニューバーには何も出ない: `crates/mac/src/files.rs:299-312`(経路未接続)、`322-344`(集計条件不一致)、`355-365`(集計が間に合わない)、`396-403`(前の転送中)、`391-395`(送れるものが無い)
- 拒否すると `Refused` 状態になり、**離すまで境界を越えられない**: `crates/mac/src/tap.rs:2101-2108`、状態機械 `crates/mac/src/file_drag.rs:120-126` / `43-45`
- 通知は `osascript` のサブプロセス実行で、しかも数百 ms 遅れる旨がコメントに明記: `crates/mac/src/main.rs:60-92`
- 通知は数秒で消える(通知センターに残るが、カーソル位置の近くには何も出ない)

**ユーザーが実際に取る行動と結果**
「もう一度端へ勢いよく当てる」→ `EDGE_AT_EDGE` がリセットされているため到達回数が数え直しになり、ダブルタップ設定(`switchDoubleTap`)なら**さらに2回**境界に当てる必要がある(`crates/mac/src/tap.rs:2044-2071`)。それでも拒否理由が解消していなければ同じ結果。「壊れた」と判断して ⌘C → Windows 側で Ctrl+V に切り替える(通知の「少し待ってもう一度掴んでください」を読めた場合のみ正解にたどり着く)。

**改善の方向**
掴みが拒否されたことを、離す前に・カーソルの近くで・理由つきで示す。掴み直しを要求する文言なら「今このまま離しても Mac 内のドロップとして成立する」ことも同時に伝える。通知(バナー)だけに依存しない。

### F2. Windows 側で「掴んだまま待たされる」が、待ち時間も残量も手元に出ない【頻度: 高 / 痛み: 最大】

**何が起きるか**
Windows の Explorer からファイルを掴んで境界の帯へ入れると、まず**全ファイルが別接続で Mac の受信フォルダへ転送され**、その完了を待ってから Mac 側でネイティブドラッグが始まる。ユーザーはマウスボタンを押したまま、相手が用意できるまで待つ。

**根拠**
- 帯に入れた時点で `DragOffer` を送って準備を始める: `crates/win/src/dragdrop/edge.rs:269-325`
- 開始通知は **合計 8MB を超えるときだけ**: `crates/win/src/dragdrop/edge.rs:315-323`(「境界で押したまま待つと、準備後に相手へ移ります(サイズによって数十秒以上かかることがあります)」)。**8MB 以下は完全に無言**
- Mac 側は `dragdrop::start` まで押下が続いているかを 500ms だけ待つ: `crates/win/src/dragdrop.rs:66`、`544-560`
- Mac 側は受信完了後に隠しパネル(32×32、透明、アイコンだけ)でドラッグを始める: `crates/mac/src/incoming_drag.rs:237-300`、`340-400`、`crates/mac/src/incoming_drag.rs:502-508`
- 待ちの上限は 30 秒で、超えると **無言で取り消し**: `crates/win/src/dragdrop/edge.rs:486-506`(`!p.sending && p.began.elapsed() > 30s` → `cancel_current()`。通知なし)
- 進捗はツールチップとステータス窓の状態行のみ: `crates/win/src/tray.rs:410-416`、進捗文字列は `crates/mac/src/files.rs:779-789` と同型

**ユーザーが実際に取る行動と結果**
「いつまで押していればいいのか分からない」→ 数秒で痺れや不安から離してしまう → 離した時点で `Claim::Released` になり **OLE ドラッグは始まらず、Win→Mac なら保存のみ**(`crates/win/src/xfer.rs:499-526`)。「やっぱり渡せなかった」と誤解する。あるいは30秒待たされて、通知もなく消える。

**改善の方向**
押したままの間に、(a) 残りバイト/%、(b) あと何秒で自動取消か、(c) 待たずに「コピーとして渡す」代替を、カーソル近傍か Windows のタスクバー付近で見せる。8MB 閾値ではなく**準備が 200ms を超えたら出す**。

### F3. 離すタイミングで結果が変わることを、離す前に知らされない【頻度: 中 / 痛み: 大】

**何が起きるか**
Win→Mac で「押したまま待って、準備完了後に離す」とドロップになるが、**準備完了前に離すとただの受信保存**になる。同じ操作なのに結果が変わるのに、どちらの状態なのかが手元で分からない。

**根拠**
- `ready` かつ `committing` のときだけ `DragCommit` を送る: `crates/win/src/dragdrop/edge.rs:372-391`
- 押下が終わっていれば「受信のみ扱い(クリップボードは変えません)」で通知だけ: `crates/win/src/xfer.rs:499-526`
- Mac 側の commit 処理は押下が続いていることを要求: `crates/mac/src/incoming_drag.rs:477-486`

**ユーザーが実際に取る行動と結果**
「置けたつもりで離す」→ 実体は `Downloads\Knit` に保存されただけで、開いている Explorer には何も現れない。通知には保存先パスが書かれているが(`crates/win/src/xfer.rs:517-524`)、その場で開く導線は無い。

**改善の方向**
「今離すと: コピーで保存 / 今離すと: その場に置ける」を状態として見せる。離した結果が保存側になった場合は、**その場でフォルダを開ける**導線を通知に付ける。

### F4. 転送中の進捗と中止が、見ている画面と一致しない【頻度: 高 / 痛み: 大】

**何が起きるか**
Mac→Win の掴み渡しでは、転送そのものの進捗は Mac のメニューバー(アイコンが「43%」のような文字になる)に出る。ところがユーザーは Windows 側を見て「置けたのか?」を確認している。Windows 側のバルーンは完了時だけで、受信中の進捗%は原理的に測れない。

**根拠**
- Mac のメニューバー題名は進捗%に差し替わる: `crates/mac/src/gui.rs:2338-2356`、進捗文字列 `crates/mac/src/files.rs:771-789`
- 転送中は中止項目がメニューに現れる(`転送を中止する(…・Esc でも可)`): `crates/mac/src/gui.rs:2379-2399`、中止実行 `crates/mac/src/gui.rs:319-322` / `2044`
- Mac の受信側は「ファイルを受信中」の文言だけで % を出さない: `crates/mac/src/files.rs:798-806`、`crates/mac/src/gui.rs:2342-2347`
- Windows はツールチップと状態行のみ: `crates/win/src/tray.rs:410-416`

**ユーザーが実際に取る行動と結果**
Windows を見ているので進捗に気づかず、「終わっていないのに次のファイルを掴む」→ `前の転送中です` で拒否(`crates/mac/src/files.rs:396-403`、Windows側は `crates/win/src/xfer.rs:218-225`)。中止したいときは Mac のメニューを開くか Esc を押す必要があり(`crates/mac/src/gui.rs:2388`)、Windows 側の操作系には中止の導線が見当たらない(Windows は Esc 検出のみ: `crates/win/src/xfer.rs:180-205`)。**未確認**: Windows のトレイメニューに中止項目があるかは未確認(今回 tray.rs のメニュー定義を精読していない)。

**改善の方向**
「今どちらへ何が流れているか」を、操作している画面側に出す。特に Win 側を見ている間に Mac→Win 転送が進む場合は、Windows のトレイで受信中を明示する。

### F5. ドロップしたのに「貼り付け待ち」に化けることがある(掴み経路のみ)【頻度: 中 / 痛み: 大】

**何が起きるか**
Mac→Win の掴み渡しで、Windows 側が「押下がもう続いていない」と判断すると、OLE ドラッグを始めず**クリップボードに載せるだけ**になる。保存自体は成功しているので、Mac 側は「送信しました(Ctrl+V で貼り付け)」と成功通知を出す。バルーンも「Ctrl+V で貼り付け可」。**「置いた」のに置かれていない。**

**根拠**
- 判定は `dragdrop::claim` の結果次第: `crates/win/src/xfer.rs:457-475`
- `Released`/`Unknown` でドラッグにしなかった場合の分岐: `crates/win/src/xfer.rs:499-526`(この経路は「保存のみ」)
- 予告の遅着を待つ窓は 500ms だけ: `crates/win/src/dragdrop.rs:66`、`crates/win/src/xfer.rs:464-471`

**ユーザーが実際に取る行動と結果**
「置けたはず」と思って Explorer を見る → 何も増えていない → もう一度掴んでやり直す。あるいは通知の「Ctrl+V で貼り付け可」に従って貼り付ける(結果としては成功するが、**ドラッグ&ドロップとして成功していない**)。Mac 側の「送信しました」通知はこの場合も出るため、成功/失敗の区別がユーザーにはつかない。

**改善の方向**
掴み経路が「ドロップにならなかった」ことを明示的に知らせる(成功通知と同じ見た目にしない)。「Ctrl+V で貼り付けてください」を同一通知に統合する。

### F6. 完了後の「どこに保存されたか」が Windows 側で見えない【頻度: 高 / 痛み: 中】

**何が起きるか**
Mac→Win の受信ファイルは `%USERPROFILE%\Downloads\Knit` に保存される。通知は「実体は C:\Users\…\Downloads\Knit」と出すが、**そのフォルダを開く導線はこの通知には無い**。

**根拠**
- 保存先の決定: `crates/win/src/xfer.rs:478-484`
- 完了通知の文言: `crates/win/src/xfer.rs:544-550`(パス表示のみ)
- Windows 側に `受信フォルダを開く` メニュー項目は存在し、`Downloads\Knit` をエクスプローラーで開く: メニュー定義 `crates/win/src/tray.rs:1537-1538`、実処理 `crates/win/src/tray.rs:910-925` — **ただし受信完了通知からは繋がっていない**(トレイメニューを開いて自分で選ぶ必要がある)
- Mac 側は設定 `open_receive_folder` で受信フォルダを自動で開く: `crates/mac/src/files.rs:576-584`

**ユーザーが実際に取る行動と結果**
「Windows 側でファイルを見たい」→ 通知のパスを目で読んで、エクスプローラーを手で辿る。またはトレイメニューの「受信フォルダを開く」を探す(存在には気づきにくい: `crates/win/src/tray.rs:1537-1538`)。Mac→Win はよく使う向きなので、この手間が毎回発生する。

**改善の方向**
受信完了通知から、そのまま保存フォルダを開けるようにする。Mac 側の `open_receive_folder` に相当するものを Win 側にも持たせる。

### F7. 失敗しても再試行は自動でなく、やり直しは最初から【頻度: 中 / 痛み: 中】

**何が起きるか**
`NotConnected` のときだけ 60 秒待って再送する(`crates/mac/src/files.rs:101-124`、`crates/mac/src/files.rs:462-481`、`crates/win/src/xfer.rs:280-303`)。それ以外の失敗(接続断・時間切れ・相手側保存失敗)は**一発で終わり**、通知が出るだけ。再試行の導線は無い。

**根拠**
- 再試行ループの条件は `ErrorKind::NotConnected` のみ: `crates/mac/src/files.rs:109`、`crates/win/src/xfer.rs:288`
- 失敗通知の文言は「もう一度掴んでください」: `crates/mac/src/files.rs:498-504`、`crates/win/src/dragdrop/edge.rs:110-117`
- 中止要求が来たら即中断(60秒待ちの途中でも): `crates/mac/src/files.rs:112-118`

**ユーザーが実際に取る行動と結果**
「もう一度掴む」→ 相手側の状態(キャッシュ・経路)が変わっていなければ同じ結果になり得る。特に大きなフォルダでは走査からやり直しになる。

**改善の方向**
「もう一度」ではなく「再送」を押せるようにする。失敗の分類ごとに、待てば直るもの/設定を直すもの/相手を直すものを分けて見せる。

### F8. 大きなファイル・大量ファイルは、失敗するまで分からない【頻度: 中 / 痛み: 中】

**何が起きるか**
合計 10GiB 上限(`crates/common/src/files.rs:6`)、展開後 512 件上限(`crates/common/src/drag.rs:7`)、掴み渡しは 64 件上限(`crates/common/src/drag.rs:4`)。掴み渡しで 65 件以上だと通知が出て越境しない(`crates/mac/src/files.rs:282-291`、Win 側 `crates/win/src/dragdrop/edge.rs:155-177`)。相手側の空き容量は分からないので、1GiB 以上のときだけ注意喚起する(`crates/mac/src/files.rs:76-86`、`crates/win/src/xfer.rs:253-265`)。

**根拠**
- 上限値: `crates/common/src/drag.rs:4,7`、`crates/common/src/files.rs:6`
- 上限文言は「展開後 640 件以上(上限 512 件)」のように実際値付き: `crates/common/src/bulk.rs:369-416`
- 保存失敗の通知は「空き容量を確認してください」: `crates/mac/src/files.rs:642-658`、`crates/win/src/xfer.rs:367-386`

**ユーザーが実際に取る行動と結果**
大量ファイルを掴んだまま渡そうとして拒否される(`掴んだまま渡せるのは 64 フォルダ/ファイルまでです`)。フォルダへまとめ直して再挑戦することになるが、**64 件という数字を事前に知る手段は通知が出るまで無い**。

**改善の方向**
掴んだ時点(または掴む前)に「今回の内容はこの経路では渡せない」が分かるようにする。件数・容量・相手の空きのうち、確定できるものを先に見せる。

### F9. 転送が中断したときの「残り」が、ユーザーの手元で分からない【頻度: 中 / 痛み: 中】

**何が起きるか**
途中で切れると、保存済みの分は通知される(「受信済みの N 件は保存されています。残りは接続が戻ってから再送してください」)。ただし**何が欠けたかは分からず、自動再開もしない**。Mac の終了時は確認ダイアログで「相手側でも中途半端なままになります」と警告される。

**根拠**
- 中断通知: `crates/mac/src/files.rs:608-616`、`crates/win/src/xfer.rs:420-428`
- 終了時の確認文言: `crates/mac/src/gui.rs:2010-2048`
- 途中まで書かれたファイルの破棄: `crates/common/src/bulk.rs:729-740`(`discard_open_file`)、`1008`(Drop)

**ユーザーが実際に取る行動と結果**
「どこまで届いたか」を送信側のフォルダと受信側のフォルダで見比べる作業になる。**未確認**: 途中まで書かれたファイルが受信側に残るかどうかは実行して確かめていない(コード上は破棄する実装)。

**改善の方向**
「どこまで届いたか」を1か所で示す。欠けた分だけを送り直せるようにする。

### F10. 相手がビジー・切断・スリープ復帰のとき、掴みは「無言で何も起きない」に寄る【頻度: 中 / 痛み: 中】

**何が起きるか**
Mac 側で前の転送中に掴むと拒否され通知だけ(`crates/mac/src/files.rs:396-403`)。Windows 側でビジーだと `ファイル転送中のため開始できませんでした`(`crates/win/src/xfer.rs:218-225` ※これは ⌘C 経路)。切断中は「経路がまだ準備中」(F1 と同じ)。スリープ復帰時、掴みドラッグが中断された場合に何が見えるかは **未確認**。

**根拠**
- Mac 側の一時的な拒否: `crates/mac/src/files.rs:396-403`
- 切断時の受信ドラッグ後始末: `crates/mac/src/incoming_drag.rs:122-140`
- 経路の再接続猶予は 10 秒: `crates/mac/src/files.rs:263-274`
- Mac 受信ドラッグ中の境界切替は抑止し、初回だけ案内を出す: `crates/mac/src/tap.rs:1988-1998`

**ユーザーが実際に取る行動と結果**
「10秒待って掴み直す」を繰り返す。スリープ復帰後は Mac/Windows のどちらのモードかも曖昧になり、入力先の不一致(片方だけ切り替わっている)が残りやすい(この不一致自体を防ぐ設計意図は `crates/mac/src/files.rs:265-274` に書かれている)。

**改善の方向**
「今は渡せない、理由はこれ、解消見込みはこれ」を1か所で示す。復帰後は現在の入力先を明示する。

### F11. 名前衝突は自動リネームで、探しにくい【頻度: 中 / 痛み: 小〜中】

**何が起きるか**
同名ファイルは `名前 (n)` として保存される。通知に「同名の N 件は「名前 (n)」として保存しました」と付くので**黙って別名にはならない**が、ユーザーが期待した名前のファイルは増えない。

**根拠**
- リネーム通知: `crates/mac/src/files.rs:660-666`、`crates/win/src/xfer.rs:388-394`
- 通知本文への合流: `crates/mac/src/files.rs:557,569-575`、`crates/win/src/xfer.rs:544-550`

**ユーザーが実際に取る行動と結果**
「同じ名前で上書きされた?」と不安になる → 通知を読んで納得する、または受信フォルダを開いて確認する。改善余地はあるが、無言よりはるかに良い(§2 の維持対象)。

### F12. Windows 側は、ドロップ位置が「離した場所」と一致しないことがある【頻度: 低〜中 / 痛み: 中 / 推理】

**何が起きるか**
Win→Mac の引き継ぎ時に、Windows 側はカーソル位置を取得し、元の Explorer へ Up を注入してから OLE ドラッグを始める。この間、ユーザーはマウスを握ったままで、**カーソルが勝手に動く/元のアプリでクリックが成立する**可能性がある。

**根拠**
- カーソル位置の取得と Up 注入: `crates/win/src/dragdrop/host.rs:34,71,95`、`crates/win/src/dragdrop/edge.rs:507-514`

**ユーザーが実際に取る行動と結果**

## 2. 今できていて良い点(改善で壊してはいけない)

正直に、現行実装は「無言を作らない」方向へかなり投資している。以下は**維持すべき資産**。

1. **掴み検出の誤爆を構造で防いでいる**。押下の世代(`generation`)とペーストボードの `changeCount` の差分、移動の有無、ファイルURLの有無をすべて満たしたときだけ「掴み」とする。同じ押下での二重送信もしない。根拠: `crates/mac/src/file_drag.rs:97-104`、`110-118`、テスト `crates/mac/src/file_drag.rs:141-242`。
2. **押下を待たせない**。待機中の監視スレッドを `unpark` で即起こすため、素早いドラッグを取りこぼさない。16ms/200ms の出し分けも妥当。根拠: `crates/mac/src/file_drag.rs:8-11`、`23-27`、`crates/mac/src/main.rs:1349-1352`、テスト `crates/mac/src/file_drag.rs:269-289`。
3. **重い I/O を CGEventTap の外へ出している**。掴み検出直後にフォルダ展開とサイズ集計を別スレッドで先に済ませる(`precompute_drag_entries`)。越境時に間に合わなければ越境を断って掴み直してもらう設計(入力のタイムアウトより優先)。根拠: `crates/mac/src/files.rs:715-727`、`322-354`、`crates/mac/src/main.rs:1357-1382`。
4. **越境前に経路の準備を確認する**。「元のドラッグは合成 Up で終わるのに転送が届かない=どこにも渡らない」を防ぐため、経路が張れていなければ断る。端末切替直後だけ 10 秒の猶予窓で通す。根拠: `crates/mac/src/files.rs:263-274`、`292-312`、テスト `crates/mac/src/files.rs:854-895`。
5. **送れない項目を黙って落とさない**。シンボリックリンク等のスキップ、読めないファイル、相手側で保存できなかった件数を、名前つきで通知に含める。根拠: `crates/mac/src/files.rs:210-223`、`382-390`、`642-658`。
6. **同名衝突・保存失敗・受信拒否を必ず通知する**。設定で成功通知を抑制していても、注意があるときは `notify` に切り替えて必ず出す。根拠: `crates/mac/src/files.rs:157-165`、`564-568`。
7. **中断しても「保存済み N 件」を必ず知らせる**。根拠: `crates/mac/src/files.rs:608-616`、`crates/win/src/xfer.rs:420-428`。
8. **Esc とメニューから中止できる**(Mac)。中止は接続の切断として相手側の後片付けまで伝播する。根拠: `crates/mac/src/gui.rs:2379-2399`、`319-322`、`crates/mac/src/files.rs:758-768`。
9. **転送中はメニューバーに進捗%が出る**。受信側は「ファイルを受信中」の文言だけでも出す(何も出ない状態に戻さないことをテストで守っている)。根拠: `crates/mac/src/gui.rs:2338-2356`、`crates/mac/src/files.rs:798-806`、テスト `crates/mac/src/files.rs:814-852`。
10. **バッチ全体の整合性を守る**。予告の件数と実受信が一致しなければドラッグにしない/件数不一致を通知する。部分転送を次のドラッグに持ち越さない。根拠: `crates/win/src/xfer.rs:476-498`、`crates/common/src/drag.rs:26-64`、テスト `crates/common/src/drag.rs:246-296`。
11. **片付けが設計に入っている**。キャンセル・切断・拒否のときに受信途中のファイルを削除し、受信ドラッグの表示状態(「受信中」)を掴んだままにしない。根拠: `crates/mac/src/incoming_drag.rs:93-124`、`crates/win/src/xfer.rs:405-419`、`442-444`、`crates/common/src/bulk.rs:729-740`。
12. **送信スレッドの異常終了で詰まらない**。`TxGuard` の Drop が Busy フラグ・進捗表示・中止要求を必ず解く(パニック1回で全転送が死ぬ事故を防ぐ)。根拠: `crates/mac/src/files.rs:667-688`。
13. **転送中に終了しようとしたら確認する**。「相手側でも中途半端なままになります」と明示し、既定はキャンセル。根拠: `crates/mac/src/gui.rs:2010-2048`。
14. **1GiB 以上の送信開始前に規模と空き容量の注意を出す**(小さい転送で通知を増やさない閾値設計)。根拠: `crates/mac/src/files.rs:74-86`、`crates/win/src/xfer.rs:253-265`。
