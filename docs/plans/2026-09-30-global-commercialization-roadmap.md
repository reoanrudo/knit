# Knit 世界展開・収益化に向けた改善計画

作成日：2026-09-30
状態：改善計画の提案。製品の合格実績、販売開始の決定、価格の確定ではない。

## 1. 結論と今回の方針

**まず、MacとWindowsを毎日併用する個人が「これがない机には戻れない」と感じる品質へ仕上げ、継続利用と実際の購入を確認する。その基盤を使って、OS・端末・地域を広げる。**

ユーザーが指定した目標は、世界中で使われる水準へ改善し、収益化を検討できる製品にすること。最初の顧客は、確認済みの「MacとWindowsを併用する個人」。開発者、デザイナー、動画・3D制作者、MacとGPU搭載Windowsを併用する人を候補として、実際の利用場面から絞り込む。

製品の完成形は [製品定義](../product-definition.md) を維持する。Linux、同一OS同士、3台以上、Android・iPadOS・ChromeOSの検討対象を撤回しない。今回決めるのは、最初に価値を証明する相手と開発の順序である。タブレットをPCの追加画面・ペンタブにする方向、撤去済みの横断検索(Desk Searchとして再提案されたものも含む)、USB機器(ウェブカメラ・マイク等)をソフトだけで別PCへ付け替える構想、モニター入力の切替(Desk Scene・DDC)は採用しない。追加の調査と判断は [Desk Continuity調査](../research/2026-09-30-desk-continuity.md) を参照。

「世界で使われる」は、翻訳数やダウンロード数だけでは判断しない。導入できる、日常利用が続く、困ったときに復旧できる、運用を継続する収入が得られる、という段階ごとの実績で判断する。

## 3. 市場で何を選ばれる理由にするか

2026-09-30確認の公式情報では、Deskflowは無料で入力・クリップボード共有、TLS、Wayland対応を提供する。Synergy個人版は買い切りで、Lite $15、Plus $19、Max $29と案内されている。Logitech Flowも対応機器を使ってMac/Windows間の入力・テキスト・画像・ファイル共有を提供する。機能の存在だけでKnitの独自性は証明できない。[Deskflow公式](https://github.com/deskflow/deskflow)、[Synergy価格](https://symless.com/synergy/purchase)、[Flow公式](https://www.logitech.com/en-gb/software/flow)

狙う価値は、次の3つの仮説として検証する。

1. **Macのキーボードとトラックパッドのまま、Windowsでも作業が途切れない。** ショートカット・スクロール・キー配列・文字入力を主要アプリで確かめる。
2. **持ち物と音が机をまたいでも、結果を信頼できる。** ファイル・フォルダ・画像を内容一致で受け渡し、音声は出力先と切断時の復元が分かる。
3. **導入・翌日の再接続・トラブル解決を、自分で終えられる。** 手動の設定ファイル編集や、開発者の助けを通常の手順にしない。

「競合より速い・安定している・唯一の機能」とは比較試験前に表示しない。既存ツール利用者を含め、同じ机・同じ操作課題で導入時間、失敗、復旧、日々の手間を比べる。設定を公平に揃え、相手の版・OS・機器を記録する。

### 基盤設計で先に揃えるもの

- 接続：`Device / Session / Capability / Permission` を分ける。端末ごとの登録・失効を扱い、通信経路の向きと操作の向きを分離する。
- 入力：物理キー、文字、ショートカットを区別する。IMEの未確定文字を全OS間で必ず移せる前提は置かず、越境時の振る舞いを決める。
- 操作権：複数PCのローカル入力と転送入力が競合した際の取得・引き継ぎ・期限・切断解放を決める。Mac/Windowsのclient/server反転だけを双方向操作の完成と呼ばない。
- 転送：操作IDと転送ID、待機・受信・確定・取消・失敗の状態を統一する。ファイル転送が入力や緊急復帰を塞がない構造にする。
- OS境界：入力取得/注入、クリップボード、画面、権限、電源状態をOSごとの実装に分ける。既存コードを機能ごとに移し、挙動変更と構造変更を小さく分ける。
- 更新：対応機能の交渉、設定移行、署名した更新情報、改変拒否、途中終了、旧版復帰を設計する。アプリのコード署名だけで更新経路まで保護できるとは扱わない。

公開上は、未確認のUAC・保護デスクトップ操作を対応済みとしない。未対応のときも利用者がローカルへ復帰できることを必須とする。

## 7. 収益化の設計

### 最初の推薦：公式製品の買い切りと、必要な人への継続サポート

低い継続サーバー費用で動く机上のツールとして、最初は買い切りを検証する。月額制は、継続的に支払う価値が確かめられてから判断する。

現在のコードはMITで公開され、LICENSEは再配布・販売を含む許可を記載している。**「オープンソースだから売れない」わけではないが、公開コードの機能を課金で独占できる前提も置かない。** 公式署名済み配布物、簡単な導入、検証済み更新、互換性確認、サポートを購入対象として明確にする。自前ビルドや再配布が可能なことを隠さない。別の有料モジュールやライセンス変更を採るなら、依存関係・権利関係・貢献者方針を別途確認して決める。[現行LICENSE](../../LICENSE)

価格は市場価格の断定ではなく、次の仮説を小規模に検証する。

| 案 | 提示する価値 | 検証すること |
|---|---|---|
| 買い切り $29 | 対応機能を備えた公式版と、明示した更新・標準サポート期間 | 無料代替がある中で、導入と信頼性に対価が支払われるか |
| 買い切り $49 | 同じ製品に、明示した初回設定支援等を加える | 支援の需要と、対応時間を含めた採算が合うか |
| 任意の年間サポート/次のメジャー版更新 | 継続的な互換性対応・追加支援等。内容と期間を明示 | 既存ユーザーの再購入理由を作れるか。初回販売前に強制しない |

試用期間は14日を仮案とし、導入成功後から数える。価格・通貨・税表示、試用後の利用条件、返金・サポート期間を販売画面で明示する。購入完了率だけで価格を決めず、返金・利用継続・対応工数も見る。

暗号化、ローカル復帰、共有停止、登録取消は全利用者の基本品質とする。期限切れや決済確認の障害で突然入力を奪わない。ライセンス確認は共有通信と分離し、オフライン利用・猶予・PC買替え・再インストール・払い戻し時の振る舞いを設計する。

### 採算を判断する計算

1件当たり貢献利益＝税を除く実受取額 − 決済等の手数料 − 返金の期待費用 − 顧客ごとのサポート/配布変動費。

月の必要販売数＝（固定費＋維持開発に充てる額）÷ 1件当たり貢献利益。貢献利益が0以下なら価格・支援内容・導入品質を修正する。

例として、1件の貢献利益を仮に $20、月の必要額を仮に $2,000 と置くと100件/月が必要になる。これは需要や収益の予測ではない。決済手段の実費、署名費、対応時間、返金率が分かった段階で実値に置き換える。買い切りの累計売上を月次の継続収益として表示しない。

### 販売前に用意するもの

公式ページ、英日ヘルプ、対応表、制限、試用/返金/更新/サポート条件、プライバシー説明、購入メール、ライセンス復元、問い合わせ、障害告知、脆弱性窓口を揃える。国際決済・税処理・返金運用を含む販売手段を比較し、販売地域と販売者の要件を確認する。契約・証明書取得・有料サービス加入は所有者が確定する工程として記載し、準備作業を先に進める。

## 8. 世界展開の順序

期間は優先順位の目安であり発売日の約束ではない。Mac/Windowsの有料初版と重なる基盤設計は先行できる。

| 段階 | 広げるもの | 開始・完了の判断 |
|---|---|---|
| 最初の検証 | 英語・日本語でMac/Windows併用者へ届ける | 外部30人のうち英語利用者10人以上を目標。両言語の導入・継続・購入理由を記録 |
| 初版後3〜6か月の評価 | 3台以上、同一OS、Windowsからの操作、主要な国際キー配列 | 端末別の認証・機能交渉・操作権が揃い、対象構成を個別に合格判定。要望件数と購入/継続への影響で順序を決める |
| 初版後6〜12か月以降の評価 | Linux、Androidの一般向け導入、追加言語 | LinuxはX11/Wayland・デスクトップ環境ごとに確認。AndroidはUSBデバッグ等への依存と配布条件を検証し、PC操作・データ共有・入力の方向を分ける |
| 個別検証を継続 | iPadOS・ChromeOS、作業の引き継ぎ、将来の計算資源連携 | OSの公開APIと許可された役割を確認。実現した機能ごとに提供し、全面対応を約束しない |

世界展開の最初の通過点として、3か国以上・北極星指標の定義を満たす100の机、D30継続60%以上、返金とサポートを含めた貢献利益の黒字を暫定目標にする。これは「世界規模を達成した」判定ではなく、拡大投資を判断するための実績である。100の机以降も、1,000・10,000の机へ拡大した際の互換性・サポート・更新の負荷を追跡する。

集客は、30秒程度で「カーソル移動→Mac流ショートカット→ファイル受け渡し→音声集約」が伝わる実演、実機で確認した比較、英語の検索向け導入記事、開発者/クリエイター向けの机の事例から始める。既存PR動画は、宣伝する全操作が候補版で再現できるか確認して使う。投稿・広告・協力依頼の実行は別途行う。

大量広告は、導入成功・継続・購入・貢献利益が分かるまで増やさない。新言語は希望者数だけでなく、利用継続とサポート可能性を見て選ぶ。

## 9. 主要リスクと分岐

| リスク | 先に確かめること | 結果に応じた対応 |
|---|---|---|
| 無料代替との差が弱い | 既存ツール利用者の同じ作業を観察し、戻りたい理由/戻りたくない理由を聞く | UI・信頼性で差がないなら訴求を変えるか、特定の作業へ焦点を絞る |
| 継続して使われない | 導入成功者のD14/D30、机構成、併用頻度 | 宣伝より先に、頻出する不具合や共有できない操作を直す |
| 買われるが採算が合わない | 顧客ごとの対応時間、返金理由、更新費用 | 導入を改善し、支援範囲と価格を見直す |
| 署名後もWindowsの警告が出る | クリーン環境のSmartScreen/Smart App Controlで導入を確認 | 署名だけで警告が必ず消えるとは案内しない。配布経路と説明を改善する |
| OS拡大で品質を落とす | 能力・許可・操作権を共通化し、対応組み合わせを明示 | 共通基盤を使い、構成ごとに試験。全OS一斉発売を固定条件にしない |
| タブレットの権限/導入が難しい | 公開APIと通常の利用者が行える導入で役割を検証 | 操作方向と共有対象を調整し、できない機能をUIから案内する |
| 旧版混在で壊れる | 安定版と直前の対応版の機能・鍵・設定互換 | 明示的に機能を停止し、更新案内と復帰を用意する |

Windowsでは、新しい署名済みバイナリでも評判が蓄積するまで警告が出る可能性があり、EV証明書による即時回避も保証されない。MacはDeveloper ID署名・公証と、更新後の実際の権限継続を別々に確認する。[Microsoft公式](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)、[Apple公式](https://developer.apple.com/developer-id/)

## 11. 計画の維持と判断記録

週1回、対応表、未解決の重大問題、導入成功、継続率、問い合わせ時間、購入/返金を見直す。各指標を「合格・未達・未測定」に分ける。修正の優先順位は、操作/データを守ること→導入成功→継続→購入理由→対象拡大の順に決める。

90日目の判断は次の通り。

- **品質・継続・購入が達成：** 合格した構成で有料提供を継続し、同一OS/複数PC等の次の対象を選ぶ。
- **品質または継続が未達：** 売り方を広げず、上位の問題を直して固定した新候補版で再試験する。
- **品質と継続は達成、購入が弱い：** 価格・無料代替との差・支援の価値を検証し、課金の追加実装へ先に投資しない。
- **対象者を集められない：** 技術だけを進める判断を避け、対象者への接点と訴求の実験を先に行う。
