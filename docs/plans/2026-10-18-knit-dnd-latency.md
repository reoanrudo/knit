# Knit ドラッグ&ドロップ体感遅延の実測(2026-10-18)

対象: HEAD `da92e17`(cargo test 548 passed / 0 failed、作業ツリーはクリーン)。
製品コードは変更していない。計測用コードは `/tmp/knit_dnd/` と
`crates/common/examples/dnd_latency.rs` のみで、後者は計測後に削除した。

## 0. 先に結論

1. **掴み検出はボトルネックではない。** MouseDown から `Phase::Ready` まで、
   1 ファイルで期待 8.0ms / 最悪 16.0ms、512 件でも期待 13.7ms / 最悪 21.7ms。
   人間が「掴めた」と感じる閾値(概ね 100ms)に対して 1 桁小さい。
2. **集計は 150ms 予算に対して 2 桁余裕がある。** 512 件の
   `collect_with_skips` は中央値 1.14ms(予算の 0.76%、約 131 倍の余裕)。
   ただしキャッシュが冷えた場合・ネットワークボリュームは未測定(§4)。
3. **体感のボトルネックは転送そのもの。** Wi-Fi 実効 30MB/s と仮定すると、
   1GB で **34.1 秒**、10GB で **341 秒(5 分 41 秒)**。Windows 側が OLE ドラッグを
   ファイル到着後に始める設計なら、この間ユーザーはボタンを押し続けることになり、
   **1GB 以上のドラッグは設計として成立しない**。ここが唯一の設計上の問題点。

## 1. 測定方法

| 項目 | 内容 |
|---|---|
| マシン | Apple M1 Pro / 16GB / macOS 26.5.2 (25F84) |
| ビルド種別 | `knit-common` は `cargo run --release`(`debug_assertions=false` を実行時に確認)。ペーストボード計測は `rustc -O` の単体バイナリ |
| 集計の反復 | 21 回(ウォームアップなし、初回を含む)。min / 中央値 / max を報告 |
| ペーストボードの反復 | changeCount 300 回、URL 読み出し 40 回 |
| 転送 | 127.0.0.1 の `TcpListener` + `TcpStream`(`TCP_NODELAY` 有効)、受信側は 4MB バッファで読み捨て |
| 転送用ファイル | `set_len` によるスパースファイル。ディスク読み出しがボトルネックにならない条件で、**プロトコル+ループバックの上限**を測る |

ペーストボード計測は `crates/mac/src/objc.rs` の `pb_files` と**同じ呼び出し列**を
再現した(`NSPasteboard` → `changeCount` → `readObjectsForClasses:options:`
+ `NSURL` + `NSPasteboardURLReadingFileURLsOnly`)。実 Finder のドラッグではなく、
同型のペーストボードを合成して読み出した値である(§4-1)。

実装上の前提(コードで確認した事実):

- MouseDown の tap コールバック内で `drag_pasteboard()` と `changeCount` を同期取得し
  `FileDrag::begin(baseline)` → `wake_watcher()`(`tap.rs:1843-1858`)。
- `EVT_LEFT_DRAGGED` で `moved()` を立てる(`tap.rs:1860`)。**移動イベントでは
  監視スレッドを起こさない**ため、検出は次の 16ms 周期に乗る。
- 監視スレッド(`main.rs:1345-1386`)は `PRESSED_POLL = 16ms` で起床し、
  `probe()` が `Some` のときだけ changeCount → ファイル URL 読み出し → `complete()`
  → `precompute_drag_entries()`(別スレッドで `collect_with_skips`)を実行する。
- 越境時(`tap.rs:2097` → `files.rs:281`)の `offer_drag_to_win` は
  `DRAG_ENTRIES_CACHE` を 10ms 間隔で最大 15 回(実質 150ms 未満)待つ。

## 2. 測定結果

### 2.1 MouseDown → 掴み検出の分解

| 段階 | 実測値 | 出典 |
|---|---|---|
| ① baseline 取得(`changeCount` 1 回) | min 0.667µs / 中央値 **0.750µs** | pb_probe |
| ② 押下通知(`unpark` → 監視スレッド復帰) | min 3µs / 中央値 **8µs** / p95 26µs | wake_probe(200 回) |
| ③ ポーリング粒度(`park_timeout(16ms)`) | 0〜16ms(一様と仮定した期待値 **8ms**、最悪 16ms) | `file_drag.rs:8`(定数) |
| ④ changeCount 再読み出し | 中央値 **0.750µs** | pb_probe |
| ⑤ ファイル URL 読み出し(1 件) | min 0.014ms / 中央値 **0.019ms** | pb_probe |
| ⑤ ファイル URL 読み出し(100 件) | min 1.020ms / 中央値 **1.091ms** | pb_probe |
| ⑤ ファイル URL 読み出し(512 件) | min 5.251ms / 中央値 **5.702ms** | pb_probe |
| ⑥ `complete()` + precompute スレッド起動 | 数十µs 未満(スレッド spawn のみ) | コード |

合計(MouseDown → `Ready` = ①+②+③+④+⑤+⑥):

| ケース | 期待値 | 最悪値 |
|---|---|---|
| 小さいファイル 1 個 | **約 8.0ms** | 約 16.0ms |
| 100 個 | 約 9.1ms | 約 17.1ms |
| 512 個 | **約 13.7ms** | 約 21.7ms |

読み方: 支配項は ③ の 16ms ポーリングで、ファイル URL 読み出しは
512 件でも 16ms の 1/3 程度。**掴み検出を速くしたいならポーリング間隔しか効かない**
(URL 読み出しの最適化は体感にほぼ寄与しない)。

### 2.2 集計(`collect_with_skips`)の所要時間

`strict=true, allow_dirs=true, keep_empty_dirs=true`(掴みドラッグ経路)。
21 回の min / 中央値 / max。

| ケース | 展開後の件数 | min | 中央値 | max |
|---|---|---|---|---|
| 1 ファイル(4KB) | 1 | 0.002ms | **0.002ms** | 0.011ms |
| 100 ファイル(1 ディレクトリ) | 100 | 0.230ms | **0.237ms** | 0.401ms |
| 512 ファイル(1 ディレクトリ) | 512 | 1.092ms | **1.142ms** | 2.376ms |
| 512 ファイル(`strict=false`・通常送信経路) | 512 | 1.119ms | 1.385ms | 2.047ms |
| 深いフォルダ(40 階層 × 3 ファイル) | 117 | 1.050ms | **1.178ms** | 1.832ms |
| 512 個を個別パス指定(掴み上限 64 超) | 512 | 0.742ms | 0.864ms | 1.541ms |

**150ms 予算との比較**: 最悪ケース(2.376ms)でも予算の **1.6%**、中央値では 0.76%。
余裕は約 **63〜131 倍**。深いフォルダでも階層あたりの追加コストは無視できる
(40 階層で 1.18ms)。

注: 掴みの上限 `drag::MAX_FILES = 64` は**トップレベルのパス数**の制限なので、
512 件のケースは現実には「512 個のファイルを 1 つのフォルダとして掴んだ」場合に起きる。

### 2.3 転送開始から最初のバイトまで(127.0.0.1 疑似ピア)

転送スレッドが `send_entries` を呼び出してから、受信側が最初のバイトを読むまで。

| 転送量 | 予告→初バイト |
|---|---|
| 1MB | **0.051ms** |
| 100MB | **0.344ms** |
| 1GB | **0.133ms** |
| 10GB | **0.284ms** |

いずれも 1ms 未満で、ループバックの write がそのまま返る速度。
**ただしこれは「オファーが本線に積まれてから」ではない**(§4-4)。

### 2.4 実効速度と「押し続けなければならない時間」

| 転送量 | 実測速度(loopback) | 実測所要時間 | Wi-Fi 実効 30MB/s 換算 |
|---|---|---|---|
| 1MB | 438.7MB/s | 0.002s | **0.033s** |
| 100MB | 487.9MB/s | 0.205s | **3.3s** |
| 1GB | 496.9MB/s | 2.061s | **34.1s** |
| 10GB | 482.1MB/s | 21.240s | **341s(5 分 41 秒)** |

補足:
- loopback の 480〜500MB/s は**プロトコルとループバックの上限**であり、
  Wi-Fi の実効速度ではない。Wi-Fi は 30MB/s(240Mbps)を一般的な値として仮定した。
- 10GB(10240MB)は `send_entries` の上限チェックを通過して送信できた。
  **つまり 10GB のドラッグは製品の上限内であり、この問題は現実に起こり得る。**
- Wi-Fi 実効 30MB/s のとき、Windows 側が OLE ドラッグをファイル到着後に始める
  設計では、ユーザーは 1GB で 34 秒、10GB で 5 分 41 秒ボタンを押し続ける。

### 2.5 上限超過・スキップの通知まで

| 項目 | 実測値 |
|---|---|
| 513 件の検出(`collect_with_skips` が `Err` を返すまで) | min 1.121ms / 中央値 **1.312ms** / max 1.925ms |
| 拒否ラベルの生成(`send_error_label`) | **0.667µs**(生成結果「展開後 513 件以上(上限 512 件)」) |
| 通知の可視化(`osascript display notification`) | **133ms / 144ms / 255ms**(3 回。プロセス起動を含む実測) |
| 64 パス上限の判定(`paths.len() > MAX_FILES`) | 走査前の比較のみで実質 0ms(通知コストだけ) |

掴み経路では、513 件の `Err` は**掴み検出時点**に precompute スレッドが
`DRAG_ENTRIES_CACHE` へ書き込み済みなので、越境時に走査は走らない。
したがってユーザーが拒否を知るまで = 境界到達 + **133〜255ms**(osascript の起動待ち)。
`notify()` はスレッド spawn で即座に戻るため、**tap スレッドは止まらない**
(入力の瞬断は起きない)。リンク等の `skipped` も同じ経路で同じ時間。

## 3. UX への含意

1. **掴み検出(最大 21.7ms)は体験のボトルネックではない。** 改善対象にしない。
   強いて言えば 16ms ポーリングが支配項で、これ以上縮める価値は薄い。
2. **150ms 予算は妥当で、余裕もある。** 実測 1.14ms(512 件)。深いフォルダも同じ。
   ただしこの余裕は「ウォームな APFS」での値であり、**冷えたキャッシュや
   ネットワークボリュームでは別**。150ms を超えると越境が拒否される
   (`files.rs:346-364`)ので、ここだけは実機の遅いケースで再測定する価値がある。
3. **本当のボトルネックは 2.4 の「押し続ける時間」。** 体験設計の要求は
   「押下保持時間を転送量の関数にしない」こと。
   - 〜10MB(0.33 秒以下): 現行の「掴んで越える」で成立する。
   - 100MB(3.3 秒): すでに長い。押し続けを前提にしない方がよい。
   - 1GB 以上(34 秒〜): **OLE ドラッグをファイル到着後に始める設計では不可能**。
     ドロップを先に受理して受信を待つ、進捗を通知で出す、などの設計変更が必要。
     数字の上では 1GB が設計の分岐点。
4. **Wi-Fi の実効速度が製品の体験を決める。** 今回測った 480〜500MB/s は
   上限値であり、実際の体感は Wi-Fi の実測(未測定)で決まる。1GB の 34 秒は
   30MB/s 仮定の計算値であって実測ではない。
5. **拒否の通知は 133〜255ms かかる。** 「瞬時に断る」体験にはならないので、
   ドラッグ中の視覚フィードバック(カーソル形状など)を併用する方が体感が良い。
6. 512 件の URL 読み出し 5.7ms は 16ms ポーリングに埋もれる。問題なし。

## 4. 測れなかった項目(正直に)

1. **実 Finder のドラッグでの読み出し**: 合成したペーストボード(`writeObjects:` で
   NSURL を載せたもの)を読んだ。API の呼び出し列は `pb_files` と同一だが、
   Finder が実際に載せる表現・項目数・所要時間は実測していない。
2. **冷えたディレクトリキャッシュ / ネットワークボリューム / 散在する小ファイル**の
   `collect`: すべて APFS のウォームな状態で測定した。150ms 予算に対する
   余裕が最も薄くなる条件はここで、未測定。
3. **Wi-Fi 実機の実効速度**: 30MB/s は仮定値。loopback は上限値のみ。
   Knit の実転送速度(本線・フレーム処理込み)は測っていない。
4. **DragOffer(本線)→ Windows 側の受理 → OLE ドラッグ開始**までの実時間:
   Windows 実機が必要(`crates/win` は触らない制約)。今回測った「予告→初バイト」は
   転送スレッドが `send_entries` を呼んでから受信側が読むまでで、
   本線のメッセージ往復・相手側の判断・OLE 開始は含まない。
5. **MouseDown からユーザーが実際にマウスを動かし始めるまで**の時間(人間の操作)。
   掴み検出の合計は「動き始めてから」の値であり、体感全体はこれに操作時間が加わる。
6. **CPU/メモリ負荷下**(音声転送中・大量の入力中)の collect 時間。
7. **150ms 待ちが実際に発生する頻度**: ログ(`[drag] mac->win 対象外`)の集計は
   行っていない。構造上ほぼ起きないはずだが、発生率は未計測。
