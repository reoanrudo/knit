## 0. 先に結論(3行)

1. **中心課題は「押下保持時間を転送量の関数にしない」こと。** 実測で 1GB=34.1 秒、10GB=341 秒
   (Wi-Fi 実効 30MB/s 仮定)。待たせ方の工夫では解決しない。**ドロップを先に受理し、転送を後から流す**
   (9/28 設計の段階3 = `drag.lazy`)以外に道がない。
2. **ただし macOS だけで先に出せる価値が大きい。**「離す前に決まっている」体験
   (渡せる/渡せないの理由・今離すとどうなるか・結果の3状態)は、Windows 側の遅延提供を待たずに
   F1・F3・F4 の痛みを消す。遅延提供が入った後も**同じ表示が「もう離してよい」に切り替わるだけ**で、
   表示の設計は作り直さない。この「後で意味が反転する表示」を成立させるため、判定はすべて
   共通クレートの純関数に置く(§3)。
3. **掴み検出(8〜22ms)と集計(512件で中央値 1.14ms)は触らない。** 実測が「既に十分」と言っている
   場所を弄らないことが、この設計の前提である。

## 1. 目標体験の定義

### 1.1 「喜ぶ」の4条件(この4つが同時に成立したときだけ喜ばれる)

| # | ユーザーが感じること | 支える機構 |
|---|---|---|
| **G1 確信** | 掴んだ瞬間に「これは渡せる」と分かる。渡せないなら**手を離す前に**理由が分かる | 掴み判定を理由つきの値にして、カーソル近傍に出す(I1・I2) |
| **G2 解放** | 境界を越えた後、**待たされていない**。「置ける場所を選べる状態」か「先に届けて後で置く状態」かが分かる | 遅延提供(I8・I9・W1)＋「今離すとどうなるか」の予報(I2・I4) |
| **G3 決着** | 離した直後に「置けた / 保存された / 失敗した」が**言い切られる**。成功を装わない | 3状態の結果モデルと通知コンポーザ(I5・W4) |
| **G4 回復** | 失敗しても、次の一手が手元にある(やり直しが最初からでない) | 失敗の記録とメニューからの再送・フォルダを開く(I6・W5) |

### 1.2 避けたい感情と、それを今まさに生んでいる機構

| 避けたい感情 | 現在の発生機構 | 出典 |
|---|---|---|
| **不安**(何も起きない) | 拒否は通知バナーだけ。カーソル近傍には何も出ない。通知は `osascript` 起動で 133〜255ms 遅れ、数秒で消える | F1、実測 2.5 |
| **壊れた疑惑**(置けていないのに成功に見える) | 掴み経路が保存で終わっても Mac 側は無言(C1)。Windows は「保存しました」だけで、置けたのかどうかは言わない | F5・C1・C4 |
| **待たされ**(押し続ける) | 全データ受信後に OLE/NSDragging を開始するため、押下保持時間＝転送時間(1GB=34.1秒、10GB=341秒) | 実測 2.4、F2 |
| **騙された**(後から分かる制限) | 64件・512件・10GiB の上限は、越えた後(または失敗した後)にしか出ない | F8、調査 3-5 |
| **二度手間** | 失敗後の導線が「もう一度掴んでください」しかない。保存先を開く導線も通知に無い | F6・F7 |

## 3. 設計の柱と、層の分け方

### 3.1 柱

1. **離す前に決まっている。** 掴み判定・拒否理由・「今離すとどうなるか」を、すべて
   **表示より先に値として確定**させる。表示は値の写像にすぎない。
2. **押下保持を転送量の関数にしない。** ドロップを先に受理し、実体は後から流す(遅延提供)。
   これが使えない相手・アプリでは、**無言で現行方式に化けさせず、「今離すと保存になる」と先に言う**。
3. **結果を3状態で言い切る。** `置けた(ドロップ先へ) / 保存のみ(受信フォルダ) / 失敗(理由つき)`。
   成功を装わない。既存の「無言を作らない」文化(§6)の延長であって、置き換えではない。

### 3.2 層の分け方(なぜ Windows を薄くできるか)

| 層 | 置くもの | ローカル検証 |
|---|---|---|
| `crates/common`(純関数) | 掴み判定の理由(`Verdict`/`Refusal`)、離す前の予報(`ReleaseForecast`)、HUD の位置決め、結果の3状態と通知文言(`DeliveryOutcome`/`compose_notice`)、遅延提供の目録と状態機械(`Manifest`/`LazyHandoff`) | **可**(cargo test) |
| `crates/mac`(配線) | 判定を呼ぶ・HUD を出す・通知を出す・NSDraggingSession を開始する | **可**(cargo test ＋ 目視) |
| `crates/win`(薄い配線) | 同じ純関数を呼び、Windows 固有の UI(OLE・層付きウィンドウ・トレイ)へ流すだけ | **不可**(§5) |

方針: **判断はすべて common の純関数、OS 依存は「命令を実行するだけ」**。
これは 9/28 設計 §3 の方針をそのまま引き継ぐ。新しい判断を `crates/win` に書かない。

### I1. 掴み判定を「理由つきの値」にする

- **何を変えるか**: `offer_drag_to_win` の8つの拒否分岐(`crates/mac/src/files.rs:282-403`)を、
  `drag::Refusal`(理由の enum)＋`drag::Verdict::{Ready{count,total,largest}, Refused{reason, next_step}}`
  に集約する。判定は純関数 `verdict_for(signals) -> Verdict` として common に置き、
  mac 側は**既存の文言をそのまま**この値から組み立てる(文言を1文字も変えない)。
- **なぜ**: F1(痛み最大・頻度最高)。実測で拒否判定そのものは µs オーダー、遅いのは通知の可視化
  (133〜255ms)なので、**値にすれば表示を差し替えられる**。F8(上限を事前に知る)も同時に解ける。
- **対象ファイル**: `crates/common/src/drag.rs`(enum・純関数・表テスト)、
  `crates/mac/src/files.rs`(notify 呼び出しを verdict 経由へ)
- **検証方法**: `cargo test -p knit-common`
  — 8分岐の表テスト(`refusal_reason_covers_every_reject_branch`)で、理由と**現行文言と同一の文字列**を固定する
  (characterization test。文言の退行を検出)。`cargo test -p knit-mac` で、`offer_drag_to_win` が `None` を
  返す全経路が verdict を残すことを確認。
- **リスク**: 文言が2箇所に散る。→ 文言は enum 側にのみ持ち、既存テストに現行文字列を写してから置換する。
- **行数の目安**: 120〜150

### I2. 「今離すとどうなるか」の予報を1つの値にする

- **何を変えるか**: `drag::ReleaseForecast` を追加する。
  `ForecastInput { phase, peer_lazy: bool, sent, total, elapsed_ms, peer_deadline_ms, refusal }`
  → `Forecast::{ WillPlace, WillSaveOnly{dir}, WaitingForPeer{percent, eta, remaining_ms}, WillFail{refusal}, Unknown{why} }`。
  ETA は「総量が確定していて、速度が2サンプル以上取れているときだけ」出す。
- **なぜ**: F2(待ち時間と残量が手元に出ない)、F3(離すタイミングで結果が変わるのに分からない)、
  調査 M2(確からしいときだけ残り時間を出す)・M3/H4(成功を装わない)。
  **両方向で必要なので common に置く**=Windows は配線だけ(§5 W3)。ここが層分けの要。
- **対象ファイル**: `crates/common/src/drag.rs`(または `drag/forecast.rs`)、
  `crates/common/tests/drag_handoff.rs`(結合テスト)
- **検証方法**: `cargo test -p knit-common` — 表テストで
  (a) `total == 0` なら ETA を出さない、(b) 経過が相手の期限を超えたら `WillFail`、
  (c) 押下が離れたら `WillSaveOnly`、(d) `peer_lazy == true` なら bulk 未完でも `WillPlace` 側に倒れる
  (c・d は遅延提供後に意味が反転する部分。ここを先に固定しておくのが I4 の下準備)、
  (e) 入力が欠けたら `Unknown{why}` を返し、成功語を出さない。
- **リスク**: 入力の出所が両側で揃わないと嘘の予報になる。→ 入力 struct は最小限にし、未確定は必ず `Unknown`。
  「解消見込み(あと何秒で経路が張れるか)」は**推定しない**(現在のコードからは分からない。§9-5)。
- **行数の目安**: 140

### I3. 拒否理由をカーソル近傍に出す(この増分だけで F1 が消える)

- **何を変えるか**: `crates/mac/src/hud.rs` を新設し、非アクティブ・クリック透過の小さな `NSPanel` で

  `hud::place(cursor, size, screen_bounds) -> (x, y)`(画面外へはみ出さない。右下優先、入らなければ左/上へ反転)。
  生成・表示は**メインスレッドのタイマー経由**(`crates/mac/src/incoming_drag.rs:237-300, 396` の作法を流用)。
- **なぜ**: F1(「離す前に・カーソルの近くで」)。通知は 133〜255ms 遅れて数秒で消え、カーソルの近くに出ない(実測 2.5)。

- **対象ファイル**: `crates/mac/src/hud.rs`(新規)、`crates/common/src/hud.rs`(place の純関数)、
  `crates/mac/src/tap.rs`(拒否時に呼ぶ)
- **検証方法**: `cargo test -p knit-common` — `place` の表テスト(4隅・マルチディスプレイ・負座標・

  カーソル近傍に理由が出て、そのまま離すと Mac 内のドロップになること。
- **リスク**: AppKit のスレッド規約(tap スレッドから `NSPanel` を触ると落ちる/出ない)。

### I4. 転送中に「待つ/離してよい」を出す(Mac→Win)

- **何を変えるか**: Mac→Win の掴み渡し中、カーソル近傍に I2 の `WaitingForPeer{percent, eta, remaining_ms}` を
  出し、状態が変わったら文言を切り替える。%=既存の `XFER`(`crates/mac/src/files.rs:771-789`)を再利用。
  更新は 250ms に間引く(純関数で丸めるので、ちらつきはテストで固定できる)。
- **なぜ**: F4(進捗が「見ている画面」に出ない。掴んでいるのは Mac 側なので、この向きは Mac の HUD が効く)、
  F3(離すとどうなるか)。**遅延提供(I8)が入ると同じ入力で文言が「もう離してよい」に反転する**。
  表示の実装を変えずに意味が反転するのが、I2 を common に置いた狙い。
- **対象ファイル**: `crates/mac/src/hud.rs`、`crates/mac/src/files.rs`、`crates/common/src/drag.rs`(予報の入力追加)

## 7. 実装しないと決めたこと(と、その理由)

| # | やらないこと | 理由 |
|---|---|---|
| 1 | **macOS でネイティブドラッグを後から合成する** | Finder のドラッグは Finder が所有し、Knit は CGEventTap で**観測しているだけ**である。離した後に Knit が同じドラッグを継続することはできない(`NSDraggingSession` は新しい押下を要求する)。**だから「離す前に決める」「離してから転送する」の2択しかない**。この事実が本設計の形を決めている |
| 2 | 掴み検出の高速化 | 実測で 8〜22ms(人間の閾値 100ms に対して1桁小さい)。支配項は 16ms ポーリングで、縮める価値が薄い(実測 2.1・§3-1) |
| 3 | `collect_with_skips` の最適化 | 512件で中央値 1.14ms(150ms 予算の 0.76%)。**冷えたキャッシュ・ネットワークボリュームの再測定**(実測 §4-2)は行う価値があるが、最適化はしない |
| 4 | 新しい `caps` 能力交換機構の新設 | 既に `PeerFeatures` 版ゲートが生きた設計(訂正 C2)。同等の機能を二重に持たない |
| 5 | 通知バナーにアクションボタンを付ける | `osascript display notification` では不可能(`crates/mac/src/main.rs:64-91`)。回復動線はメニューバーに置く(I6)。`UNUserNotificationCenter` への移行は権限・配備の別課題 |
| 6 | ドラッグ中のアニメーション・効果音 | 調査 L3「出典で確認できない以上、模倣しない」 |
| 7 | 速度のために暗号化を切る | 調査のアンチパターン(localsend README)。**やらない** |
| 8 | 無言の上書き | 調査 H2・Warpinator #135。既存の `create_unique`(自動リネーム＋通知)を維持する。上書きを選べるようにする場合も、削除を伴う操作の前に必ず1回確認する |
| 9 | フォルダの置換受信(既存を消す) | 調査 H3・Warpinator #205。既存は一時ファイル→rename なので、**同名でも既存を丸ごと差し替える経路を作らない** |
| 10 | 転送の再開(レジューム)・内容の差分送信 | 9/28 設計にも無い。遅延提供(I8・I9)が入れば「待たされる」問題の主因は消える。まずそこに投資する(§9-9 の積み残し) |
| 11 | 同時転送の複数本化 | `FILE_TX_BUSY` は1本のまま(`crates/mac/src/files.rs:668`)。調査 H4 の「同時実行は1本のまま」を維持。遅延提供でも増やさない |
| 12 | 摩擦doc F12(ドロップ位置のずれ)の修正 | 推理であり未再現(摩擦doc §3-5)。本設計の対象外。実機で再現したら別タスク |

## 9. 設計の弱点・未検証の前提(正直に)

1. **Wi-Fi 実効 30MB/s は仮定値**である(実測は loopback の上限 480〜500MB/s のみ。実測 §4-3)。
   実効が 100MB/s なら 1GB=10秒で、遅延提供(W1・I8・I9)の緊急度は下がる。
   **最初に測るべきは「実際の Wi-Fi 実効速度」**であり、この設計はその仮定に依存している。
2. **Explorer が `DoDragDrop` 終了後も `IStream` を読み続けるか**は未検証(9/28 設計 段階3 の PoC 1)。
   不成立なら W1 は中止し、「掴んで渡す=保存」を**明示的な UX**(先に「置けないので保存になります」と言う)
   に切り替える。無言で化けさせない(I2 の予報がその受け皿になる)。
3. **`CF_HDROP` しか受けないアプリ**では遅延提供が使えない。出し分け(9/28 設計 段階3)は未解決。
   アプリによって置けない可能性を、事前に言えるようにする必要がある。
4. **カーソル近傍 HUD(macOS)の実現手段が未検証**。`NSPanel` を tap スレッドから扱えないため、
   `incoming_drag.rs` の作法(メインスレッドのタイマー)を流用する。実機で「出る・消える・
   クリックを奪わない」の確認が要る。出せない場合の代替は通知文言の改善のみで、
   **F1 の改善幅は大きく下がる**(I3 はこの設計で最も不確実な増分)。
5. **「解消見込み」(あと何秒で経路が張れるか)は推定しない**。現在のコードからは分からないため、
   予報は「今は渡せない理由」までに留める。嘘の見込み(「10秒お待ちください」)を出さない。
6. **摩擦doc の `crates/win` 側の引用は再確認していない**(`edge.rs:486-506` の30秒取消、
   `tray.rs` のメニュー構成、`host.rs:34,71,95` の Up 注入)。§5 の W2・W5 の前提は未確認であり、
   実装前に読むこと。
7. **F5 は Mac 単独では消えない。** I5 で文言は正しくなるが、Mac が結果を知るには W4 が要る(C1)。
8. **テストで担保できない部分**が残る: 通知バナーの実表示時間、Finder/Explorer の見た目、
   Wi-Fi の実測、`IStream` の寿命。9/28 設計 段階6(E2E 手順書)が要る。
9. **遅延提供中のキャンセル**で、Explorer/Finder が読み続けているデータを断ったときに
   部分ファイルが残るかは未確認(9/28 設計 段階3 の PoC 2)。I8 の終端条件は
   「一時ファイルを必ず捨てる」だが、**相手アプリが掴んでいる実体**までは消せない。
10. **本設計は 548 passed の状態のコードを読んで書いた**。cargo build / cargo test は実行していない
    (設計タスクのため)。各増分の着手時に、まず基準の緑を確認すること。

## 10. 実装の順序(まとめ)

```
I1 → I2 → I3 → I4 → I5 → I6          … macOS だけで出せる(Windows を待たない)
                    ↘ I7 → I8 → (PoC) → I9
W4 → W5 → W1 → W2 → W3                 … Windows 実機が要る(独立して先に出せるものから)
```

- **最初に実装すべきは I1(＋I2)**。理由: 痛み最大(F1)で、macOS だけで完結し、
  後続(I3・I4・I5・I8 の表示)すべての土台になる。150 行以内で1コミットに収まる。
- I7・I8 は I4 と並行できる(I4 は `peer_lazy` を入力に持つだけ)。
- I9 は必ず PoC の後。不成立なら I9 を落とし、I4 の表示で代替する(設計は壊れない)。
- §5 の W 系は、担当できる実機・CI のタイミングに合わせて独立に進める。
