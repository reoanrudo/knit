## 1. 調査(3役が独立に実施。すべて出典・実測つき)

### 1.1 競合UX調査 → `docs/plans/2026-10-18-knit-dnd-ux-research.md`
製品10系統(ShareMouse / MWB / Logitech Flow / Universal Control / KDE Connect / LocalSend / PairDrop / Warpinator / 近距離共有 / Synergy系)を調査。

- **最も優れているのは ShareMouse の「マウス遷移を認識した時点で転送開始」**。Knit は逆(全データ受信後に越える)。
- **名前衝突は「無言の上書き」も「黙った別名保存」も不満の元**(Warpinator #135 はファイル永久消失 / LocalSend #2478 は黙った別名保存に 👍13)。Knit は後者の状態。
- 制限を**失敗後に知らせる**製品(MWB の「1ファイル100MB未満」)は不満が集中 → 「越える前に理由を出す」方針が正解。
- 避けるべきアンチパターン: 速度のために暗号化を切らせる / 検出にベンダクラウド必須。

### 1.2 ユーザー視点の摩擦棚卸し → `docs/plans/2026-10-18-knit-dnd-friction.md`
時系列(掴む→離す→転送→完了→失敗)で摩擦を列挙し、すべて `file:line` で裏取り。最悪の3件:

1. **掴みが拒否された理由が、離す前に画面に出ない**(通知バナーは数秒で消え、カーソル付近には何も出ない。しかも離すまで境界を越えられない)→ ユーザーは端に何度も当て直し、最後は「壊れた」と誤認して ⌘C 運用へ逃げる。
2. **Win→Mac の「押したまま待つ」に待ち時間も残量も出ない**(8MB 以下は完全に無言)。
3. **離すタイミングで結果が変わるのに、離す前に分からない**。

### 1.3 実測 → `docs/plans/2026-10-18-knit-dnd-latency.md`
| 項目 | 実測 |
|---|---|
| MouseDown → 掴み検出 | 1件: 期待 8.0ms / 最悪 16.0ms、512件: 期待 13.7ms / 最悪 21.7ms |
| 集計(フォルダ展開) | 512件で**中央値 1.14ms**(150ms 予算の 0.8〜1.6%) |
| 転送(loopback) | 480〜500MB/s。1GB=2.06s / 10GB=21.2s |
| **転送(Wi-Fi 実効 30MB/s 換算)** | **1GB=34.1s / 10GB=341s(5分41秒)** |
| 拒否通知の可視化 | osascript で 133〜255ms |

**結論: 掴み検出と集計は既に十分速く、弄る価値がない。唯一の設計問題は「転送量が押下保持時間の関数になっていること」。**

## 2. 設計 → `docs/plans/2026-10-18-knit-dnd-design.md`

**目標体験の4条件**: (1) 離す前に結果が決まっている (2) 待たせない (3) 成功を装わない (4) 失敗しても詰まらない。

**設計の柱**:
1. **離す前に決まっている** — 判定の理由(`Refusal`)と「今離すとどうなるか」(`Forecast`)を、表示より先に**値として確定**する。表示は値の写像にすぎない。
2. **押下保持を転送量の関数にしない** — ドロップを先に受理し、転送は後から流す(`drag.lazy`)。使えない相手には**無言で化けさせず、先に「今離すと保存になる」と言う**。
3. **結果を3状態で言い切る** — 置けた / 保存のみ / 失敗。文言を1箇所(`common::notice`)に閉じる。

**実装しないと決めたこと**(理由つき): macOS でネイティブドラッグを後から合成する(不可能。Finder がドラッグを所有しており Knit は観測しているだけ)/ 掴み検出の高速化(既に十分)/ 速度のための暗号化オフ / 無言の上書き / フォルダの置換受信 / 同時転送の複数本化。

**層分け**: 判断はすべて `crates/common` の純関数に置き、macOS と Windows は「命令を実行するだけ」にする。これにより **macOS で全遷移をテストでき、Windows 側に判断を書かずに済む**。

## 5. 検証の体制と実績

**原則: エージェントの自己申告を信用しない。** 実装役とは別の「敵対的検証役」が、自分で build/test を回し、差分を読み、**変異(わざとバグを入れる)テスト**で「テストが実効的か」を確かめた。

- 検証役が見つけた**本物の欠陥**: I2 の「50%で離す→完了」経路のテスト欠落(変異が生存)/ I5 の観測を超えた言い切り・配線が無テスト・越境直後の取りこぼし / **I3 の `setWraps:` は NSTextField に存在せず初回表示で例外**(実機プローブで確定。私の環境では画面が見えず発見不能だった)/ `press()` の反例 / I6 の記録リセット漏れ / I8 の過剰受信・二重受理・死んだ状態。
- 検証役は自分の計器の欠陥(`crates/common/tests/` を走査していなかった)も自己申告して再基準化した。
- 私(lead)は各増分で `cargo build` / `cargo test` を実行し、**変異テストで自分のテストを疑い**、CI の結果を確認した。役割ループの成果物についても independent review を回した。

**CI**: `ci.yml`(macos: `cargo test --workspace --exclude knit-win` + ベンチ回帰ガード / windows: `cargo test -p knit-common -p knit-win`)が**全 push で緑**。ベンチは「回帰なし」。

## 7. 利用者の方に試していただきたいこと

1. **ドラッグの反復**: Mac→Win でファイルを掴んで渡す操作を**何度か繰り返す** → 以前は「モード切替後に一度クリックすると全部保存のみ」でした(`c49f95d` で修正)。今は毎回置けるはずです。
2. **HUD の見え方**(唯一、目視が必要な項目): Finder で**65件以上**を選んで端へ持っていく → カーソル近傍に「掴みすぎです(64 件まで)」/ 相手を切った状態で掴む → 「転送の準備中です」。位置・大きさ・消えるタイミング・邪魔さを見てください。
3. **名前衝突の通知**: 同じ名前のファイルを渡して「名前 (1)」になった事実が通知に出るか。
4. **失敗からの回復**: 転送を失敗させ(相手を切る等)、メニューの「直前: …」「もう一度送る」で再送できるか。

## 8. 学び(次のループに効かせること)

1. **測ってから設計する。** 「掴み検出が遅いのでは」という直感は実測で否定され(8〜22ms)、真のボトルネックは別の場所(押下保持時間)にあった。
2. **役割を分けると、単一エージェントの誤りが落ちる。** ラウンド3ではユーザー役の提案をそのまま実装すると `Win+Backspace` になるところを実装役が発見し、今回の I3 では**検証役の実機プローブだけが `setWraps:` の誤りを検出した**。
3. **テストがあることと、守られていることは違う。** 変異テストを入れると「実装は正しいがテストが検出できない」穴が繰り返し出た(テストの穴6件、うち2件は等価変異)。
4. **赤いCIは、その後ろのテストを殺す。** 数週間赤だった windows ジョブのせいで `knit-win` のテストは一度も走っていなかった。push を検証ループに入れて初めて、製品バグが出た。
5. **判断を純関数に寄せ、配線を1行にする。** 「配線が無テスト」という指摘が繰り返し出たため、判定を `common` の純関数へ出して呼び出し側を1行にする形が有効だった。
6. **できないことは、できないと書く。** 画面の目視・Windows 実機の対話操作・実行時検証は、この環境では原理的に不可能。設計書と報告書に明記し、利用者の確認項目として切り出した。

- 次の増分は「**受信を staging へ流す経路**」: `Msg::Manifest` を受けたら `DragAccept` を返して即ドラッグを開始し、
