# ドラッグ＆ドロップ アップグレード設計

作成：2026-09-28。対象：ファイルを掴んだまま画面境界を越える機能（Mac⇄Windows）。
前提資料：[調査](../drag-drop-investigation.md)、[Win→Mac計画](2026-09-27-windows-to-mac-drag.md)、
[コードレビュー](../reviews/2026-09-28-drag-review.md)。引き継ぎ手順は [引き継ぎ書](2026-09-28-drag-handoff.md)。

状態：設計提案。未承認・未実装。各段階の「実機確認」は利用者の操作を要する。

## 1. 目標

製品要件 D02（ファイルとフォルダを渡す）・D03（整合性と再開）・D04（アプリへのドロップ）を満たす。
利用者から見た完成形は次のとおり。

1. Finder/Explorer で掴み、境界を越え、相手の狙った場所で離すと置ける。両方向で同じ操作になる。
2. 大容量でも境界で待たされない。離した時点で行き先が確定し、転送は裏で続く。
3. 取消（Esc・元のPCへ戻る・切断）で、勝手な完了・クリップボード変更・部分ファイルの公開が起きない。
4. フォルダ・多数項目を構造ごと渡せる。渡せないものは越える前に理由が分かる。
5. 「受信完了」「OSがドロップを受理」を区別して表示する。成功を装わない。

## 3. 設計方針

- **ドラッグ（操作）と転送（データ）を分ける。** 調査 §4 の推奨構造を採用する。操作は本線（24900）で軽量に、データは bulk で運ぶ。両者は ID で結ぶ。
- **状態機械は共通クレートに置き、純粋関数としてテストする。** OS 依存コード（COM/objc）は状態機械の出力（「OLE を開始せよ」等）を実行するだけにする。
- **段階ごとに単独で出荷できる形にする。** 各段階は旧版の相手と接続を保ち、機能は相手の能力を確認してから有効にする。
- **版番号の比較から能力の交換へ移る。** hello に `caps`（文字列の集合）を足す。例：`drag.id`、`bulk.hash`、`bulk.cancel`、`drag.lazy`、`bulk.tree`。未知のキーは無視する。
- **実機確認を段階の完了条件に含める。** API 単体の成功を操作全体の成功と扱わない。

## 4. 段階別の設計

各段階の工数は不確実性が大きいため示さない。規模感だけを S/M/L で示す。

### 段階0：現行版の実機確認（規模 S・前提）

新機能の前に、現行版の操作を固定手順で確かめる。ここで出た不具合は段階1より優先する。

| 手順 | 期待 |
|---|---|
| Finder の小ファイル1件を掴んで越え、Explorer のフォルダで離す | そのフォルダへコピー、原本は残る |
| 同じ操作で、越えた直後にすぐ離す | ドロップまたはクリップボード受信のどちらか。別の物を掴まない |
| 離した後に別のウィンドウを掴む | 前のファイルが混ざらない |
| フォルダを掴んで境界へ | 通知が出て越えない。離せば Mac で普通にドロップできる |
| Explorer の小ファイルを接続辺の青い帯へ運び、Finder で離す | コピーされる。Windows 側の原本は残る |
| 上の操作で、Mac へ移った後に Esc | 取り消され、Downloads/Knit の受信物が片付く |

ログの確認点：Mac `/tmp/knit-mac.log` と Windows `knit-win.log` の `[drag]` 行。

### 段階1：転送層の信頼性（規模 M・D03）

目的：部分データを完成品として公開しない。取消を送信側から伝える。後段の遅延提供の土台にする。

1. **一時保存→検証→原子的公開。** 受信は `名前.knit-part` へ書き、FILE_END で検証後に `rename` する。切断・取消・検証失敗では削除する。起動時に残骸を掃除する。
2. **内容ハッシュ。** FILE_END の本体に SHA-256（または BLAKE3。依存追加は要判断）を載せる。現行の受信側は FILE_END の本体を読まないため、旧版は無視できる。
3. **転送ID と取消フレーム。** `CANCEL(id)` フレームを追加し、送信側・受信側のどちらからでも止められるようにする。受信側からの取消は本線のメッセージで送る。
4. **進捗イベント。** 受信側にも `Progress { id, received, total }` を出し、段階5の表示に使う。
5. **転送ジョブの一元化。** Mac の `FILE_TX_BUSY` を、キュー（直列・上限つき）に置き換える。転送中の次の掴みは「待ち」として受け付け、拒否しない。

受け入れ：中断・再起動・同名・送信中の元ファイル更新で、誤った完了・内容不一致・範囲外書き込みがない。単体テストに加え、`crates/common/tests/` に大容量・中断の結合テストを足す。

### 段階2：ドラッグ状態管理の共通化（規模 M）

目的：方向ごとに散った状態を1つの状態機械へまとめ、取消・結果・複数台を一貫して扱う。

```
Idle → Offered → Accepted → Transferring → Ready → Handed(OSドラッグ中) → Dropped{copied} | Cancelled{reason}
```

- `crates/common/src/drag.rs` に `Session { id, direction, peer, phase, files, deadline }` と遷移関数を置く。入力は「予告・受諾・転送完了・押下解放・Esc・モード離脱・切断・時間切れ・OS結果」、出力は「OLE/NSDragging開始」「取消送信」「受信物の片付け」「通知」などの命令列にする。
- 既存の `Incoming`・`Carried`・edge の `Pending`・Mac の `ACTIVE`/`COMMIT` をこれに置き換える。
- Mac→Win でも `DragDone { id, copied }` を返し、Mac 側の通知とログを OS の結果に合わせる。
- 複数台：セッションに相手IDを持たせ、非アクティブな相手のメッセージを遷移させない。取消だけは相手を問わず受ける（残留防止）。
- 表形式のテストで全遷移を固定する（不正な遷移は無視されること、各終端で片付けが一度だけ起きること）。

### 段階3：転送完了前のドロップ（規模 L・PoC 先行）

目的：大容量でも境界で待たせない。調査の問題1。

- **Windows で受け取る側（Mac→Win）：** OLE の `CFSTR_FILEDESCRIPTORW` + `CFSTR_FILECONTENTS`（`IStream`）で、メタ情報を先に、実体を後から渡す。`IDataObjectAsyncCapability` に対応した受け手（Explorer）には非同期で渡す。`IStream::Read` は転送ジョブの受信済み範囲を待って返す。
- **Mac で受け取る側（Win→Mac）：** `NSFilePromiseProvider` で、ドロップ先フォルダへ後から書き出す。書き出しはメインスレッド外のキューで行う。
- **CF_HDROP（実パス）しか受けないアプリ：** 仮想ファイルでは受けられない。現行の「境界で完了を待ってから実パスで渡す」方式を代替として残す。両方の形式を同時に出すと Explorer が CF_HDROP を優先し得るため、出し分けを PoC で決める。
- **PoC で先に確かめること（ここで不成立なら段階3は中止し、段階5の待機表示で代える）：**
  1. Explorer が FILEDESCRIPTOR/FILECONTENTS の遅延 `IStream` を、DoDragDrop 終了後も読み続けるか（非同期モード）。
  2. `IStream` の読み出し中に転送が失敗した時、Explorer が部分ファイルを残すか。
  3. Finder が File Promise の書き出し完了を待つ間の表示と、失敗時の挙動。
  4. COM オブジェクトの寿命（DoDragDrop 後もデータオブジェクトを保持する責任）。

### 段階4：フォルダ・多数項目（規模 M）

- **目録（manifest）：** 転送開始時に `{相対パス, 種別(file/dir), サイズ}` の一覧を送る。FILE_BEGIN の JSON に `rel` を追加し、受信側は一意なトップフォルダの下に構造を再現する。空フォルダも作る。
- **名前の規則：** Windows の予約名（CON, NUL, COM1…）、末尾の点・空白、`: * ? " < > |`、大文字小文字だけが異なる名前の衝突、長いパス（260文字超）を送信前に検出し、変換規則か拒否理由を示す。既存の `files` モジュールの無害化を拡張する。
- **シンボリックリンク：** 辿らない。リンク自体も送らず、目録で「除外」と示す。
- **上限：** 件数の上限（現 64）は目録で扱える範囲まで引き上げ、合計サイズで制限する。
- Mac の掴み検出はフォルダ URL を既に取得できる。Windows の edge は `is_file` 条件を外し、目録作成へ回す。

### 段階5：体験（規模 M）

- 受信側のカーソル付近に、件数・進捗・取消方法を示す小さな表示を出す（Windows は層付きウィンドウ、Mac は非アクティブパネル）。
- 境界で転送を待つ間（段階3が使えない相手）の表示と、待機中の Esc 取消。
- 同名衝突の扱い（自動リネームの明示、または選択）。
- 結果表示：「受信済み（Downloads/Knit）」「ドロップ先へコピー済み」「ドロップ先が受け付けず受信フォルダに保存」を区別する。
- 通知の連投防止（同一理由は一定時間内に1回）。

### 段階6：検証基盤（規模 S〜M・各段階と並行）

- Windows の対話試験：一時スケジュールタスクで実行し、必ず削除する手順をスクリプト化する（前回の `knit_live_drag_test` の手順）。試験中は通常アプリを止め、失敗時も必ず復帰させる。
- Mac の AppKit 試験：`incoming_drag::probe` を拡張し、File Promise の構築も検証する。
- E2E 手順書：段階0の表をアプリ別の対応表（Finder、Explorer、デスクトップ、ブラウザのアップロード欄、Office、Photoshop 等）へ広げ、結果を `output/` に JSON で残す。

## 5. プロトコルの互換方針

| 追加 | 旧版の相手の挙動 | 有効化の条件 |
|---|---|---|
| hello の `caps` | serde の既定値で空 | — |
| FILE_END の本体にハッシュ | 本体を読まず無視 | 相手の caps に `bulk.hash` |
| `CANCEL` フレーム | `_ => {}` で無視（取消は効かない） | 相手の caps に `bulk.cancel` |
| FILE_BEGIN の `rel` | 無視して平置き | 相手の caps に `bulk.tree`。無ければフォルダを拒否 |
| 遅延提供 | — | 相手の caps に `drag.lazy` |

`VERSION` は caps を導入する段階で 14 に上げる。`MIN_VERSION` は 11 のまま。

## 6. 主なリスク

| リスク | 影響 | 対策 |
|---|---|---|
| 遅延提供が Explorer/Finder で期待どおり動かない | 段階3が成立しない | PoC を先に行い、不成立なら待機表示に切り替える |
| 自前 COM vtbl の誤り | 即時クラッシュ | 新インターフェースごとに SDK の IID とメソッド順を照合するテストを追加する（既存の `ole_can_query_the_standard_drop_source_interface` と同じ方式） |
| 境界切替と受信ドラッグの競合 | 操作不能・入力の奪い合い | 段階2の状態機械で「OSドラッグ中は境界切替しない」を一元化し、時間切れでの回収を保つ |
| 並行エージェントの編集衝突 | 手戻り | 引き継ぎ書の手順（mtime 確認・worktree）に従う |
