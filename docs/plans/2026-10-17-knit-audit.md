# Knit コード監査(多視点)2026-10-17

## このリポジトリは何か

Mac と Windows の間でマウス・キーボード・クリップボード・音声を共有する常駐アプリ(Knit)。
Android タブレットを「もう1台の画面」として使う経路もある。想定負荷は**1人の利用者と数台の端末**で、
アプリは何日も起動したままになる。したがって「無言で機能が死ぬ」「履歴やファイルが壊れる」
「端末を抜いた時に固まる」が最も困る問題になる。

方法: リポジトリの実コードを読み、**具体的な再現ケースが言えるものだけ**を挙げた。
性能の改善は別紙(`2026-10-17-knit-perf-final-report.md`)にまとめてあり、本稿では繰り返さない。

---

## Must fix(壊れる・失われる)

### 1. 履歴の画像だけが先に消え、履歴には残る(復元できない項目ができる)
- **これは何か**: クリップボード画像は `images/` に実体を保存し、履歴には「ファイル名+サイズ」だけを残す。
  保存時に `prune_image_store(dir, IMAGE_KEEP=60, MAX_IMAGE_STORE_BYTES=512MiB)` が**実体だけ**を古い順に削除する
  (`crates/common/src/history.rs:725-745`)。
- **問題**: 4K の画像は1枚約33MB なので、**16枚ほどで 512MiB に達する**。以降は画像をコピーするたびに
  古い実体が消えるが、**履歴の項目は残ったまま**なので、その項目を選ぶと
  「履歴の画像が見つからないため復元しません」(`crates/mac/src/clip.rs:262` 付近)になる。
- **直し方**: 実体を消すときに**同じ名前を参照する履歴項目も消す**(または「実体なし」と表示する)。
  `prune_image_store` の戻り値で消えた名前を返し、呼び出し側で履歴から取り除く。数行で足りる。
- **放置すると**: 画像を何度もコピーするだけで履歴が「押しても何も起きない項目」で埋まる。

### 2. タブレットを抜いたままコピーすると、クリップボード処理が最大60〜120秒止まる
- **これは何か**: Android へ画像を送る `set_clipboard_image` は `adb` を**同期で**呼ぶ
  (`crates/mac/src/android.rs:1087-1170`)。タイムアウトは mkdir 10秒、push は「ファイルごとに最大120秒」
  (同 1030 行付近のコメント)、ヘルパー呼び出しは 60秒。
- **問題**: 端末の電源が落ちている・USB を抜いた状態で画像をコピーすると、
  クリップボード処理がその時間だけ待つ。呼び出し元はコピー検知のループなので、
  **コピー同期全体が止まる**。
- **直し方**: 送信前に `adb -s <serial> get-state` を短いタイムアウト(2秒)で確認し、
  端末が居なければ即 false。加えて push のタイムアウトを 10〜15秒に短縮する。
- **放置すると**: 端末を外したまま PC を使うと、コピーのたびに数十秒の停止が起きる。

## Should fix(危ない・テストが無い・重複・混ざった仕事)

### 3. 「ロックが壊れたら履歴保存を黙ってやめる」
- **これは何か**: `history_save` は `if let Ok(h) = HISTORY.lock()` で、ロックが毒されていると**何もしない**
  (`crates/mac/src/clip.rs:21-40`)。
- **問題**: 履歴を触っている最中にどこかで panic すると、以後その実行の間ずっと
  **履歴が保存されない**(ログにも出ない)。
- **直し方**: 毒されていても `into_inner()` で中身を取り出して保存を続け、1行だけ警告を出す
  (同じファイル内の他の箇所は既に `unwrap_or_else(|e| e.into_inner())` を使っている)。
- **放置すると**: 気づかないまま履歴が更新されなくなる。

### 4. 一時ファイルの後始末が「最善努力」で、名前の検証も無い
- **これは何か**: 端末へ送る前に `std::env::temp_dir().join(name)` へ画像を書く(`android.rs:1092`)。
  送信後に消すが `let _ =` なので、途中で落ちると残る。
- **問題**: (a) 強制終了時に**画像のコピーが /tmp に残る**(機密になり得る)、(b) `name` に `/` が入ると
  **temp の外へ書ける**(今の呼び出し元は安全だが、関数は `pub`)。
- **直し方**: `name` を `Path::new(name).file_name()` に通してから join し、
  起動時に古い `Knit-*.png` を掃除する。作成は 0600 で行う(`write_private` 相当)。
- **放置すると**: 共有 Mac で画像が残る/将来の呼び出し追加で外へ書く。

### 5. Android 経路のテストが6件しかない(実機なしで増やせる)
- **これは何か**: `crates/android-bridge` は1ファイル6テスト、`mac/android.rs` は1769行。
  性能ループ12で**スタブ adb を注入する計測テスト**を1本作った(起動回数と所要時間を検証)。
- **問題**: push・クリップボード設定・端末検出の分岐が、実機がないと検証されない。
- **直し方**: ループ12のスタブを共通ハーネス化し、`get-state`/`push`/`content query`/`app_process` の
  引数と失敗時の戻り値をテストする(既に1本成功している型を流用)。
- **放置すると**: adb まわりの変更が実機で初めて壊れる。

### 6. Windows 側のテストが薄い(CI は走っているので足すだけ得)
- **これは何か**: `crates/win` は15ファイル23テスト。`.github/workflows/ci.yml` は `windows-latest` で
  `cargo test --workspace` を実行している。
- **問題**: 入力変換・トレイ状態・設定の往復にテストが無く、macOS では**コンパイルすら確認できない**。
- **直し方**: 優先度は (1) `input.rs` の変換表、(2) 設定の保存/読込の往復、(3) トレイの状態遷移。
- **放置すると**: Windows 固有の変更が無検証で入る。

### 7. 計測器が CI で回っておらず、改善が戻っても気づけない
- **これは何か**: `examples/perf-*.rs` と `tests/perf_image.rs` に計測器が揃っているが、手で実行するだけ。
- **問題**: 今回の改善(転送・履歴I/O・音声・adb)は、将来の変更で静かに戻り得る。
- **直し方**: `scripts/bench.sh` で全部を表形式にまとめ、CI では代表3本だけ実行して
  **コミットした基準値から20%超の悪化で失敗**させる(計測のばらつき±10〜30%を踏まえた閾値)。
- **放置すると**: 同じ最適化を何度もやり直すことになる。

## Nice to have(小さな改善)

### 8. ログが `/tmp` のみで、再起動やクリーンアップで消える
- **これは何か**: Mac のログは `/tmp/knit-mac.log`(+`.old` へ5MBで1世代退避、`main.rs:474-500`)。
- **問題**: macOS は再起動や一定期間で `/tmp` を消すため、**昨日の障害を調べられない**。
- **直し方**: 診断実行時に `~/Library/Logs/knit/` へコピーを残す(1世代でよい)。

### 9. 実行時に残る一時ファイルの掃除
- **これは何か**: `/tmp` の `Knit-*.png`(上記4)と、テストが作る `knit-*` ディレクトリ。
- **直し方**: 起動時に `Knit-*.png` を消す。テストは `TempDir` 相当で確実に消す。

### 10. 巨大ファイル(変更頻度の高い所から分割)
- **これは何か**: `mac/tap.rs` 3270行、`mac/main.rs` 2000行超、`android.rs` 1769行、`audio.rs` 1751行。
- **問題**: 読むにも直すにも時間がかかり、今回のように**同じ処理が2箇所**生まれやすい
  (性能ループ10で `dib_to_rgba` の二重実装を実際に発見・統合した)。
- **直し方**: 振る舞いを変えずに移動だけのコミットで、`android.rs` を adb / display / input / clipboard に分ける。

## 直し方の順序(推奨)

1. **1番**(履歴の画像と項目の不一致) — 数行で直り、利用者が直接困る。
2. **2番**(端末を抜いた時の長時間停止) — プリチェック1回で解消。
3. **7番**(CI で計測) — 今回の成果を守る。
4. **5・6番**(テストを足す) — 実機なしで増やせる。
5. 3・4・8・9・10 — 小さな修正をまとめて1回で。

## 判定

- **Verdict**: 健全な土台(CI・権限・乱数・ログ運用は良い)。まず **1番と2番**を直すべき。
- **Lean**: 今回の作業で重複実装を1件統合済み。追加の削除候補は**未検証**(計測器と一時ファイルは残す価値がある)。
- **未確認**: GUI の初回セットアップ体験 / Windows 実機での入力・トレイの挙動 / 更新の失敗時ロールバック /
  `docs/reviews/` の旧指摘のうち今回確認していない項目。
