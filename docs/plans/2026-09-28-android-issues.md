# Android 連携の残課題の整理(2026-09-28)

実機(Xiaomi Pad 6S Pro 12.4 / HyperOS 3 / Android 16 / USB)での利用者の確認結果と
コード調査を突き合わせた整理。**修正はまだ行わない。優先順位は利用者が決める。**

## 現状

- 成功している: マウス共有(ポインタ・クリック)、キーボード共有、画面配置(画面端での行き来)、
  テキストのクリップボード共有(双方向)
- 問題のある 3 領域: ①トラックパッドの諸機能 ②画像・ファイルの共有 ③設定画面での Android の扱い
- なお切替直後に Mac へ即戻る問題は 2026-09-28 に切替後 400ms の猶予を入れて修正済み
  (未コミット。main.rs `enter_win_mode_cursor_lock` と abs-edge 戻り判定)

---

## 領域 1: トラックパッド

### 症状(利用者の回答)

スクロール・ピンチ・ジェスチャ等のトラックパッド機能がタブレットに適用されていない
(すべて未適用と認識されている。詳細な差は未聴取)。

### 原因

**縦スクロール(細かさの問題。効いているが粗い可能性が高い — 推測)**

- 第 1 層: Mac は 0.05 ノッチ刻みの `Msg::Scroll` を送る
  (`crates/mac/src/main.rs:3840`-3877、量子化 q=0.05)。一方 Android 中継の
  `Pointer::scroll`(`crates/mac/src/android/hid.rs:361`-372)は `trunc()` で
  **整数ノッチになるまで貯め、1 カウント単位のホイールレポート**しか出さない。
  Mac 側の細かい刻みがすべて捨てられ、1 ノッチ分溜まるまで端末に何も届かない
- 第 2 層: `MOUSE_DESC`(`hid.rs:9`-19)は Resolution Multiplier(高解像度ホイール)を
  持たない、scrcpy 4.1 準拠の旧来の記述子。Windows 側は 120 units/notch の
  高解像度スクロールとして受けられるが、この経路では構造的に伝えられない
- 結果の推測: Mac の除数 60(px→ノッチ)に対し、ゆっくりスクロールでは 1 ノッチ
  (Mac で 60px 相当)溜まるまで無反応となり「効かない」ように感じる。
  速く動かせば動くはず。**全く効かない場合は別原因(UHID ホイールを HyperOS が
  無視する等)の可能性があり、実機での切り分けが必要**

**横スワイプ(実装はある。実機で効くか未確認)**

- Mac 側は `SWIPE_NAV`(既定 ON)で横優勢ジェスチャを「戻る/進む」の
  `Msg::MouseButton` btn 3/4 に変換(`main.rs:3801`-3837)
- Android 中継は btn 3/4 を HID ボタン 4/5 として送る(`hid.rs:342`-358)。
  Android がボタン 4/5 を戻る/進むとして扱うかは実機未確認
- 横優勢と判定されたジェスチャは縦成分も含めて握りつぶされる(`main.rs:3837`)

**ピンチ・三本指スワイプ(未実装)**

- Mac 側のイベントタップマスク(`main.rs:4497`-4514)に EVT_GESTURE(型 29)が無く、
  ジェスチャを取得していない。取得していないため Android にはもちろん何も送れない。
  **Windows 向けにも実装されていない**(新機能として設計が必要)

**慣性スクロール**

- Mac の慣性は EVT_SCROLL_WHEEL の delta として届くため、上記スクロール経路に
  乗る(細かさの問題は同じ。別途実装は不要)

### 修正案と規模

| 案 | 内容 | 規模 |
|---|---|---|
| 1-A | `MOUSE_DESC` に Resolution Multiplier を追加し、count 単位で送る。端末が REL_WHEEL_HI_RES を扱う必要あり(HyperOS での動作は未知数) | 小(0.5 日)+実機確認 |
| 1-B | scrcpy の INJECT_INPUT_SCROLL(浮動小数のスクロール量・位置指定)へ切り替える。`android/scrcpy.rs` にメッセージ型の追加が必要(現在 `inject_keycode` しか無い)。UHID を介さず確実だが、ポインタ位置推定との整合が必要 | 中(0.5〜1 日)+実機確認 |
| 1-C | 横スワイプは実機確認のみで済む可能性が高い(実装済みのため) | 確認のみ(数分) |
| 1-D | ピンチ等のジェスチャは EVT_GESTURE の取得から。Windows 向けにも無い新機能 | 大(設計を含む) |

### 実機でしか確かめられない点

- 現状の縦スクロールが「粗い/遅いだけ」か「全く効かない」か
  (`adb shell getevent` で UHID の EV_REL 到達を見れば Mac 側から切替せずに判別可能。
  設定変更を伴わない読み取りのみ)
- ボタン 4/5(戻る/進む)が Android のアプリで機能するか
- Resolution Multiplier を HyperOS が解釈するか(案 1-A の成否)
- INJECT_INPUT_SCROLL の実際の挙動(案 1-B で必要)

## 領域 2: クリップボード(画像・ファイル)

### 症状

テキストは双方向で共有できている。画像・ファイルは共有できない。

### 原因

- 第 1 層: Android 中継(`crates/mac/src/android.rs`)は本線(127.0.0.1:24900)にのみ
  接続する。**大容量経路(bulk、ポート 24902)の中継を実装していない**
  (android.rs 内に bulk 関連のコードが存在しない)
- 第 2 層: Mac のクリップボード同期(`main.rs:486`-534)は、テキストは `Msg::Clip` で
  送るが、**ファイルは `send_files_to_win`(bulk)、画像は `bulk::send_image`(bulk)**
  で送る設計。bulk は独立した TCP 接続のため、中継が接続しない限り Android に届かない。
  また `Msg::Clip` 自体が `text: String` のみ(`crates/common/src/lib.rs:363`)
- 第 3 層(受信側の装置の欠如):
  - Android への画像貼り付け: scrcpy プロトコルの set_clipboard はテキストのみで、
    端末クリップボードに画像を置く手段がプロトコル上無い
  - Android からの画像・ファイル取得: scrcpy の DeviceMsg::Clipboard もテキストのみ。
    端末クリップボードの画像を外部から読む方法は adb にも無い(セキュリティ)
  - ファイルのみ、adb push で端末のストレージへ置くことが可能
    (中継が既に adb を使っているため技術的ハードルは低い)

テキストのクリップボードが動いているのは android.rs:953-959(Mac→端末)と
android.rs:779-798(端末→Mac、last_clip で折り返し防止)の実装があるため。

### 修正案と規模

| 案 | 内容 | 規模 |
|---|---|---|
| 2-A | Mac→Android へのファイル送信: bulk のイベントを android 中継で受け、adb push で Downloads 等へ保存+通知。保存先・通知・UI(履歴からの再送)の設計が必要 | 中(1〜2 日+設計) |
| 2-B | Mac→Android への画像: 2-A と同じ経路でファイルとして送る(クリップボードに画像は置けないため) | 2-A に含む |
| 2-C | Android→Mac の受け渡し: scrcpy/adb 経路では取得不可。端末側の操作(共有シート・ファイル選択)を組み合わせる設計が必要。製品定義の「方向 2」に相当 | 大(設計から) |

### 実機でしか確かめられない点

- adb push 後の通知(Notification)を設定変更なしに出せるか
- Xiaomi のファイルマネージャ/ダウンロードフォルダでの見え方

## 領域 3: 設定画面での Android の認識

### 症状

「設定画面が Windows 限定に見える。タブレットとの連携がされていないように感じる」

### 原因

- 第 1 層(文言・部品): 設定ウィンドウ(`crates/mac/src/gui/prefs.rs`)の 4 ページ
  (接続・画面配置・操作・共有)の表示がすべて Windows 前提:
  - 「Windowsの位置を、実際の画面配置に合わせます。」(prefs.rs:505)
  - 「このMac」⇔「Windows」の 2 台固定の図(prefs.rs:516-520)
  - 「Windowsへ切替」(533)、「Windowsを登録…」(593)、「Windowsは右/左/…」(628-635)、
    「Windowsへファイルを送る…」(799)、「Windowsの音声を再生」(811)、
    「Windowsスピーカーをミュート」(819)
- 第 2 層(状態モデル): 接続状態は単一の `CONNECTED`(`main.rs:2360`)、画面位置
  `SIDE` も全接続先で共通の 1 つ。Android 接続中は「Windowsの位置」が Android の
  配置を兼ねる。設定の保存も side 1 つ(`gui/preferences.rs:32, 126-127`)。
  Android 固有の状態(操作する/しない・許可待ち・接続中)はメニューバーの
  「Android タブレット」サブメニュー(`gui.rs:129, 1842-1902`、`android/state.rs:184`-)に
  しか現れず、設定ウィンドウはそれを知らない。Android 中継は `Msg::Cfg` の
  side/spk_mute を受けても無視する(`android.rs:961-964`)
- 第 3 層(製品定義との対比): 製品定義「端末ごとに利用できる機能」は、対応機能と許可を
  区別して交換し、UI は接続先で実行できる操作を示すこと、未対応・権限不足・停止中・
  通信断を同じ表示にまとめないことを求める。現状は Android が画面・ファイル・音声
  未対応でも設定画面は Windows と同じ操作を提示する(例: 音声ミュートは Android には
  無意味)。クリップボード履歴の表示名も "Windows" 固定(`main.rs:4653, 4829, 5012, 5044`。
  docs/android.md の既知の制約どおり)

### 修正案と規模

| 段階 | 内容 | 規模 |
|---|---|---|
| 3-1 | 文言の動的化(接続先が Android の時は「接続先(タブレット)」等)と、接続ページへの Android 端末状態の表示(メニューの menu_lines 相当を並べる) | 小(0.5 日程度) |
| 3-2 | 接続先モデルの導入: 端末ごとの SIDE・状態。preferences.json の保存形式拡張。複数接続(Windows+Android)時の配置エディタ | 中(1〜2 日+設計) |
| 3-3 | 機能ネゴシエーション: hello で対応機能(画面・ファイル・音声の可否)を交換し、UI が接続先でできない操作を示さない/未対応と表示する。製品定義の「まとめない」方針の実装 | 中〜大(My Desk 設計に絡む) |

### 実機でしか確かめられない点

- 特になし(エミュレーターと consent 試験で確認可能)

## 優先順位の推奨(案)

1. **縦スクロールの実機切り分け → 案 1-A または 1-B**
   理由: 最も利用頻度が高い基本操作で、体感障害が最大。まず getevent による
   切り分け(数分、設定変更なし)で「粗いだけ」か「全く効かない」かを確定し、
   前者なら 1-A/1-B の小〜中規模で解消できる見込みが立つ
2. **横スワイプ(戻る/進む)の実機確認(案 1-C)**
   理由: 実装済みで確認のみ。1 の切り分けと同時にできる
3. **設定画面の段階 3-1**
   理由: 「Windows 限定に見える」体感の直接原因で小規模。製品定義の
   「まとめない」方針への第一步として表示だけでも前に出す価値が高い
4. **Mac→Android のファイル送信(案 2-A/2-B)**
   理由: 中継が adb を持つため実現性は高いが、保存先・通知・UI の設計が要る。
   1〜3 の後に着手が妥当
5. **ピンチ・ジェスチャ(1-D)と Android→Mac の受け渡し(2-C)、段階 3-2/3-3**
   理由: Windows 向けにも存在しない機能で、単独のバグ修正ではなく製品設計
   (My Desk・方向 2)の一部として進めるべき。個別に着手すると設計が二重になる
