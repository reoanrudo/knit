## 1. ループの設計

各ラウンドは「3役が並列で思考 → シニアエンジニアが1件だけ実装」の2フェーズ。

| 役割 | 視点 | 出力 |
|---|---|---|
| **改善エージェント** | 計測可能なボトルネック(コピー/割り当て、ロック保持、同期I/O、再試行、ポーリング、変換) | `file:line` の証拠付きで1〜3件の提案 |
| **デザイナーエージェント** | Mac 側の UI/UX(トレイ、メニュー、設定、通知、文言、状態表示、一貫性) | 具体的な文言・メニュー配置まで落とした提案 |
| **ユーザーエージェント** | Mac と Windows を並べて毎日使う人の摩擦(無言の失敗、待たされる、壊れたと思った) | 利用場面を具体的に想像し、コードで裏取りした提案 |
| **シニアエンジニア** | 3役の提案から**1件だけ**選び、実装 → `cargo build` → `cargo test` → 緑ならコミット | 変化の要約と検証結果(実測値のみ) |

ラウンドごとの焦点(重複を避けるためローテーション):
①クリップボード ②ファイル転送 ③入力共有 ④音声 ⑤履歴/保存領域 ⑥接続/再接続 ⑦UI/設定 ⑧ログ/診断 ⑨アイドル時CPU/メモリ ⑩総仕上げ

**安全柵(プロンプトで禁止)**: `crates/win/**`(macOS ではコンパイル検証できない)、`.github/**`、依存の追加、`docs/plans/**` の編集、既存テストの削除・骨抜き、`push`/`rebase`/`reset --hard`/`commit --amend`。変更は150行以内、3回直して通らなければ**全破棄して正直に失敗報告**。毎ラウンド台帳を渡して**再提案を禁止**。

### リスクの高い変更の精査(lead がコードを読んで確認)

- `fdec414`(pairing): 試行回数は接続受理ごとに `attempts += 1`、**相手から1バイトも届いていない場合のみ** `attempts -= 1` で戻す。コードを送る総当たりは従来どおり数えるため、**試行制限の強度は変わらない**。probe が RST/FIN の揺れで数えられていたのが原因で、正当なユーザーが3回で Locked になっていた。
- `0c24266`(終了): 確認 → Winモード解除 → 送信中止 → 受信 bulk 切断+400ms 待ち → **画像フラッシュ** → `exit(0)` の順序を実コードで確認(レビュー指摘で入れたフラッシュが保たれている)。
- `8f6c252`(待機): `wake_watcher()` は**押下開始時のみ**(tap.rs の MouseDown 経路)。`park_timeout` は unpark トークンを消費するため、probe と park の間の起床も取りこぼさない。timeout は保険として残っている。
- `587e4b9`(接続): `connect_first` は最初に確立した1本を返し、残りは送信側の drop で閉じる(二重セッションにならない)。Windows 側は `first_reachable` のまま(未検証のため変更しない)。
- `fd8fae1`(診断): 追加される行は最大10行で並び順は不変。実装は `crates/common` にあり Windows 側のレポートにも同時に効く。

## 4. 正直な申し送り(未検証・既知の制約)

1. **`crates/win/**` は一度も変更していない**。3役は Windows 側の修正(テキスト再試行、画像転送の通知、受信フォルダを開く等)を繰り返し提案したが、macOS ではコンパイル検証できないため全ラウンドで採らなかった。Windows 実機または CI(`windows-latest`)での検証が別途必要。
2. **実機での目視確認は未実施**。UI 文言(メニュー項目、確認文、状態行)は単体テストで文字列を固定しただけで、実際のメニューバー表示は確認していない。
3. **DIBキャッシュはサイズ上限なし**(1枚のみ・次のクリップボード変化で差し替え)。8K画像では132MBが次のコピーまで残る。上限を設けると2回変換になり遅くなるため速度を優先した(コメントに明記済み)。
4. **ラウンド実行中に既存の間欠フレークが数回**観測された(pairing のネットワーク系、レイアウトの static 共有)。ラウンド10で pairing 側の**根本原因を修正**した。レイアウト側は未解決(並列実行時のみ)。
5. **エージェントの自己申告は検証していない部分がある**: 各ラウンドのA/B値(例: 605.79→108.95ms)は同一マシンの参考値で、lead は再測していない。lead が再測したのは `scripts/bench.sh` の範囲のみ。
6. 監査項目の残り: **Windows のテスト追加は依然ブロック**(`rustup` 不在で Windows ターゲットの std を入れられない)。**ファイル分割**(`tap.rs` 3270行 / `gui.rs` 3253行 ほか)は未着手。

### 次にやる価値が高い候補(3役の提案から未採用のまま残ったもの)

- `history_push_image` を所有権受け取りにし、33MB の `to_vec`(実測818µs/枚)を消す
- 画像受信直後1秒ガードによる「コピーしたのに永久に送られない」取りこぼしの修正
- `unique_final` の HashSet 化(O(N²) 解消、N=8000 で16.7倍)
- 失敗した ⌘C ファイル転送の指紋を戻す(無言の行き止まり解消)
- 履歴からの画像復元を GUI メインスレッドから出す(実測 ≥55ms の停止)
- 音声の供給枯渇時に 1.3ms のフェードを入れる(プチノイズ)
- 受信バイト数の表示(Mac は受信量を捨てている)
- ファイル分割(tap.rs / gui.rs / main.rs / android.rs)

## 5. このループで分かったこと(運用面)

- **1件制約が効く**: 「1ラウンド1コミット・150行以内」を課すと、提案が大きくても安全な一歩に分割され、全ラウンドで build/test が緑のまま進んだ。
- **役割の衝突が品質を上げる**: ラウンド3では、ユーザー役の提案(ctrlスロットを立てる)をそのまま実装すると **Win+Backspace** になることをシニアエンジニアが `win/src/input.rs:592` の対応表から見つけ、正しいスロットへ修正した。単一エージェントでは通っていた誤り。
- **「正直に失敗してよい」を明示する**: 3回で通らなければ全破棄して `no_change` を返す指示により、壊れたコミットは1件も入らなかった(10/10 コミット)。
- **検証は lead が独立に回す必要がある**: 各ラウンドの報告は具体的で信頼できるものが多かったが、テスト総数の申告と lead の実測がずれた場合は lead の値(548)を採用した。
