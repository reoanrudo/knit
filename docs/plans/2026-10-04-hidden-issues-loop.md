# 気づきにくい欠陥を探す「探検者×シニア」交互ループ(2026-10-04 実行済み)

## 目的

通常の使用・レビュー・テストでは発見できない欠陥を、専門分化した「探検者」10名が洗い出し、
シニアエンジニアがその場で修正するまでを1ペアとする交互ループで処理する。
前回の「想定ユーザー10名×シニア」(使用時の懸念・UX中心)に対し、本ループは
**故障・稀条件・組み合わせ・経年**で顕在化する類の問題を狙う。

## 実行方法(ZCode)

各ペアを直列に実行する(後のペアが前の修正後のコードを見るため)。

1. 探検者: `Agent(subagent_type: edge-case-hunter)` で以下の共通プロンプト+領域固有の観点を送る
   - 出力: 最大5件、「条件→症状→根拠(file:行)→修正方針」、最優先1件を明記
   - 実在コードのみ根拠に(推測の行番号禁止)
2. シニア: `Agent(subagent_type: builder)` に探検者の報告を貼り、全件対処させる
   - 方針: 懸念は原則すべて直す。大機能は最小の安全な代替(通知・案内・ドキュメント)
   - 検証: `cargo check/test --workspace --exclude knit-win`(winはmac上でビルド不可のため静的確認)
   - Android は gradle(`cd android && ANDROID_HOME=$HOME/Library/Android/sdk JAVA_HOME=<jdk17> ./gradlew testDebugUnitTest assembleDebug`)
   - コミットはユーザー指示があるまで禁止

## 10領域の定義(探検者ペルソナ)

| # | 領域 | 狙い |
|---|---|---|
| 1 | 並行性・レース | ロック順序・TOCTOU・Drop順序・フラグの可視性 |
| 2 | リソース枯渇 | 無限蓄積(履歴・ログ・キャッシュ)・リーク・全件書き換え |
| 3 | 部分失敗 | 1つ失敗した後の連鎖(キーチェーン拒否・ディスク満杯・JSON破損) |
| 4 | 時間・時計 | NTP跳躍・巻き戻り・スリープ境界・Instant/壁時計の混同 |
| 5 | 境界値・特殊名 | 0/1/最大・NTFS非合法名・UTF-16 units・長パス・改行入り名 |
| 6 | 機能同時使用 | ドラッグ中切断・転送中の同期・メニュー開示中の追記・切替 |
| 7 | 環境依存 | 同型マルチモニター・DPI・仮想NIC・Caps Lock |
| 8 | 状態移行・破搝 | 非アトミック書き込み・部分移行・破損JSON・mtime乖離 |
| 9 | 誤用・不正入力 | 巨大行・無制限Intent・ビーコン偽装・sweep誤削除・値域未検証 |
| 10 | 長期運用 | 常駐中のログ成長・spawn蓄積・dead entry・RETIRED残留 |

## 探検者プロンプトの骨子

```
あなたは Knit プロジェクトの「<領域>探検者」です。…(共通コンテキスト: 製品概要・crates構成)
# あなたの仕事
<領域固有の観点のリスト>
# 重点的に見る箇所
<領域ごとのファイルリスト>
# 出力ルール
日本語。最大5件。「<4行形式>」の形式。根拠は実コードのみ。修正はしない。
最後に「最優先: N件目」と理由1行
```

## シニアプロンプトの骨子

```
あなたは Knit プロジェクトのシニアエンジニアです。「<領域>探検者」の指摘5件が報告されました。
方針: 全件対処(小さく・安全に・既存パターン踏襲)。
# プロジェクト基本情報(winはビルド不可・Androidはgradle・コミット禁止)
# 報告された指摘(5件を貼る)
# 修正方針(厳守)
# 出力形式(日本語・検証コマンドと結果)
```

## 2026-10-04 実行結果

- 検出50件・対処50件(見送りは理由つきの最小代替)
- 主な成果: 双方向同時転送の修正、単調時計の共通化(clock.rs)、状態ファイルの
  アトミック化+隔離退避(persist.rs)、画像ストア512MiB上限、UTF-16名前検証、
  発見候補のポート確認、モニター識別リマッチ、DPI宣言、Caps Lock同期、
  bulk張替延期の世代ガード、ログの周期truncate ほか
- テスト: ループ開始時274件 → 終了時359件(全緑・1度だけ一時的な揺らぎを観測し再実行3回連続で全緑)
- 新規テスト約85件・Android gradle ビルド維持

## 運用の注意

- knit-win は mac 上でビルド不可: win 側変更はすべて静的確認になり、Windows 実機での
  `cargo check -p knit-win` と実動作確認が個別に必要(各ペアの報告に確認事項が残る)
- 時間依存のテストは並列実行で揺らぐことがある: 失敗したら単体再実行で確認してから修正判断
- ループ全体は未コミット変更の上に積むため、開始時点の状態を記録(コミットまたはスナップショット)
  しておくと「今回分」の切り分けと報告が正確になる
