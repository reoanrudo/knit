## 1. なぜ「まだ改善できる」のか

ループ1〜9 で測った結果、**すでに限界に達していたのは以下**である:

| 経路 | 実測 | なぜ打ち止めか |
|---|---|---|
| 入力イベントの符号化 | encode 84ns / decode 125ns | 通信レイテンシ(ms)に対し無視できる |
| bulk 転送 | 約370 MB/s(loopback) | **実回線(Wi-Fi 実効 5〜50MB/s)より1桁速い**。回線が律速で、暗号の並列化は体感に効かない |
| アイドルCPU | 0.1〜0.3% | 電池・発熱の改善余地なし |
| 入力送信ループ | 到着即送信 | 追加遅延なし |

一方、**まだ測っていない経路に大きなコストが残っている**ことが今回のコード調査で判明した。それが本設計の対象である。

## 2. 新たに特定した改善余地: 画像クリップボード経路

Mac で画像をコピーし、Android タブレットへ同期する経路(`crates/mac/src/clip.rs:438-470` → `crates/mac/src/objc.rs:209-267`)では、
4K 画像(3840×2160×32bpp = **約33MB の DIB**)1枚あたり次が走る:

| # | 処理 | 場所 | 推定コスト | 問題 |
|---|---|---|---|---|
| A | DIB→RGBA 変換 | `objc.rs:246-256` | 数十〜200ms | **ピクセルごとに `rgba.extend_from_slice(&[p[2],p[1],p[0],p[3]])`**。830万回の4バイト追加(境界チェック+容量成長)。行単位のコピーで置き換え可能 |
| B | PNG エンコード | `objc.rs:259-266` | 数百ms | 既定圧縮(`png::Encoder` 既定)+ RGBA 全面を実体化(33MB 追加確保) |
| C | DIB→BMP 変換 | `objc.rs:171-207` | 数ms + 33MB メモリ | `Vec::with_capacity(14+dib.len())` で**全面コピー**。ヘッダを足すだけなので `write_vectored`/2回書きで回避可能 |
| D | 履歴への画像保存 | `clip.rs:112-145` | 数十〜100ms + **33MB ディスク書き込み/枚** | 毎回フル BMP を書く。`prune_image_store` の走査も伴う |

**この経路はユーザー操作(コピー)ごとに走る**ため、体感に直結する(画像コピーの同期がもたつく)。
ループ1〜9 で見た「ns 級のマイクロ最適化」とは違い、**数百ms 単位が動く見込み**がある。

## 3. 計測の設計(採用判断の基準を先に固定する)

ループ5・7 の教訓(±30%の測定変動、無効なA/B)を踏まえ、**先に規律を決める**:

1. **分解して測る**: 合計時間だけでなく A〜D を個別に測る(`perf-image.rs`)。
2. **規模を大きく取る**: 4K DIB を N=20 枚処理し、p50 と p90 を報告(単発計測は使わない)。
3. **3回実行して中央値**を取り、**採用基準は「改善が実行間のばらつきを超えること(目安 +20% 以上)」**。
4. **正しさは別テストで担保**: 変換結果が**旧実装とバイト単位で一致**することをテストで検証(速度改善で内容を変えない)。
5. **トレードオフは総時間で判断**: PNG 圧縮率を下げるとエンコードは速いがファイルが大きくなる。**エンコード + 転送**の合計で比較する(転送路の実測速度を使う)。

計測器: `crates/common/examples/perf-image.rs`(画像処理は mac crate にあるため、純粋な変換ロジックを `objc.rs` の `#[cfg(test)]` ではなく**計測可能な形**にする必要がある → 「変換関数を DIB スライス→RGBA の純関数として切り出し、mac crate のテストから呼ぶ」設計にする)。

### 優先順位の根拠
- ループ10〜12 は**ユーザー操作ごとに走る経路**で、しかも未計測。ここが最大の伸びしろ。
- ループ13・14 は同じ画像経路の残り(ディスクとメモリコピー)。
- ループ15 は体感ではなく**音切れ耐性(品質)**の改善。
- ループ16 は計測できない場合 SKIP と明記して中止してよい。

## 5. リスクと差し戻し条件

| リスク | 対処 |
|---|---|
| 変換の最適化で色やアルファが変わる | **バイト同一性テスト**(旧実装との比較)を必須にする。不一致なら即差し戻し |
| PNG 圧縮を下げて転送が遅くなる | 「エンコード+転送」の合計で比較。悪化するなら既定のままとする |
| 履歴保存の非同期化で終了時に取りこぼす | 終了時のフラッシュ(`Drop`/明示呼び出し)を実装。テストで担保 |
| 背景スレッド化でディスク競合 | 書き込みは1本のワーカーに直列化し、`SAVE_LOCK` と同じ排他を維持 |
| 計測がばらついて判断できない | 採用基準(+20%)を満たさなければ**差し戻して記録のみ**(ループ5・7と同じ扱い) |

## 6. 今回も対象外とするもの(理由つき)

- **プロトコル v17(64KB レコード上限の撤廃)/ 暗号の並列化**: loopback では +10〜25% の余地があるが、**実回線が1桁遅いため体感には出ない**。Windows/Android 実機との互換検証コストに見合わない。
- **転送スループット全般**: 同上(回線律速)。
- **GUI の描画性能**: 計測手段がなく、ユーザー報告もない。
