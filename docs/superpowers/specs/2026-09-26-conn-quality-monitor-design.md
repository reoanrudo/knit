# 通信品質の監視と自動再接続(設計)

日付: 2026-09-26
ステータス: 承認待ち(ブレインストーミング: アプローチ B「品質監視のみ」+ 回復アクションは「再接続のみ」)

## 背景

- 実運用は 2 台とも同一 LAN 上だが、tsunagu の全経路(本線 24900・音声 24901・bulk 24902)は
  Tailscale IP 経由で張られている。Tailscale の直結 UDP が切れて DERP 中継へ落ちると、
  接続は維持されるまま遅延が数倍になり、操作感が劣化する
- 現状の検知は Mac 側の `tailscale status --json` ポーリング(30 秒毎)で、**通知のみ**。
  回復手段は無い
- プロトコルの `Msg::Ping`/`Msg::Pong` は既に送信時刻(unix ms)のエコーバックに対応しており、
  Mac 側は RTT を測定済み(メニュー状態行の表示用)。Windows 側は `Ping { ts: 0 }` を送っており
  測定していない。**判定・トリガは両側とも存在しない**

## 目的(と効果の限界)

- 中継劣化の**検知を 30 秒ポーリングから約 10 秒**へ短縮し、定量的(RTT 値)に行う
- 回復可能なケース(劣化した経路に張り付いた古い TCP フロー等)は**再接続で自動回復**する
- **限界(明記)**: 再接続は Tailscale 自身の経路選択(WireGuard の直結再交渉)を強制しない。
  中継に固定されている場合は新しい TCP も同じ中継を流れ、通知に留まる。
  外部コマンド(tailscale CLI 等)は本設計の対象外(ユーザー選択)

## 設計

### 1. RTT 測定(Windows 側。プロトコル変更なし)

- Windows の 3 秒毎 ping を `Ping { ts: now_ms() }` に変更し、`Pong { ts }` 受信時に
  `now_ms() - ts` で RTT を計算する
- 直近サンプルのリングバッファ(10 件)を接続セッション毎に保持する
- Mac 側の既存測定・表示・中継検知(30 秒ポーリング通知)は変更しない
- `MIN_VERSION` は据え置き(11)。旧相手でも Ping/Pong の形は不変のため相互運用される

### 2. 劣化判定(純粋関数として common へ配置)

- 入力: RTT サンプル列・設定閾値・セッション最小 RTT
- 判定: 直近 5 サンプルの**中央値**が `max(閾値, セッション最小 RTT の 5 倍)` を
  **3 連続**(≈9 秒)上回ったら「劣化」。中央値が閾値未満に戻ったら「回復」
- 二重の条件(絶対値 + 相対値)により、遅い回線での常時誤発火と速い回線での見逃しを避ける

### 3. 再接続トリガとガードレール

- 劣化判定が成立したら、既存の再接続ループ(指数バックオフ・複数候補レース)へ
  「切断」を注入する。レースと再接続の仕組み自体には手を入れない
- **クールダウン 60 秒**: 劣化による再接続は 60 秒に 1 回まで(フラップ防止)。
  pong 途絶(10 秒)による真正断は従来通り無制限
- **bulk 転送中は抑制**: ファイル転送中の再接続は転送を中断するため、転送完了を待つ。
  転送中に経路が完全に死んだ場合は pong 途絶・書き込み失敗の既存経路が拾う

### 4. 表示・ログ・設定

- 遷移時のみログ: `[net] RTT 劣化(中央値 84ms, しきい値 30ms)→再接続します` /
  `[net] RTT 回復(4ms)`。既存の `[diag]` 行に `rtt=` を追加
- Windows トレイの状態行は Mac 由来の `Stat { rtt }` でなく**自側 RTT** を表示する
  (Mac は測定継続。`Stat` メッセージ自体は残す)
- 設定: `TSUNAGU_RTT_MS`(既定 30。0 で機能無効)。docs/usage.md に追記

## テスト方針

1. 判定ロジック(common)の単体テスト: 閾値の境界・相対条件・3 連続の境界・
   回復判定・クールダウン・サンプル不足時(接続直後は発火しない)
2. cargo test での回帰(現行 common 12 件 + Mac 3 件が壊れないこと)
3. 実機検証: `TSUNAGU_RTT_MS=1` で人為的に発火させ、再接続とログ・トレイ表示を確認。
   Tailscale を意図的に中継へ落とす検証は**ユーザーの事前承認が必要**

## 非目標(YAGNI)

- LAN 直結優先・経路二重化(アプローチ A/C。今回は不採択)
- tailscale CLI 等の外部コマンド実行による回復(ユーザー選択で不採択)
- 音声・bulk の経路品質への個別対応(本線 RTT で代表する)
- Make-before-break(新接続確立後の切替)。既存の再接続機構をそのまま使う
